# ARC-004 — API Gateway

> **Objectif :** Définir l'architecture de la passerelle d'API (API Gateway) d'EduWeb Planner afin d'assurer un accès sécurisé, performant, évolutif et centralisé aux services de la plateforme.

# 1. Vision

Toutes les applications EduWeb doivent communiquer avec les services internes via une **API Gateway unique**.

Elle constitue l'unique point d'entrée sécurisé de la plateforme.

Aucun client ne doit accéder directement aux microservices.

---

# 2. Objectifs

L'API Gateway permet :

- sécuriser les échanges ;
- centraliser l'authentification ;
- simplifier les applications clientes ;
- répartir les requêtes ;
- protéger les services internes ;
- appliquer les politiques de sécurité.

---

# 4. Architecture cible

Composants :

- Reverse Proxy
- Authentification
- Routage
- Load Balancer
- Rate Limiter
- Cache
- Journalisation
- Monitoring
- Webhooks
- Circuit Breaker

# 5. Rôles de l'API Gateway

## Authentification

Validation des utilisateurs.

---

## Autorisation

Vérification des rôles.

---

## Routage

Transmission vers le bon microservice.

---

## Agrégation

Fusion de plusieurs réponses.

---

## Protection

Filtrage des attaques.

---

## Observabilité

Mesure des performances.

---

# 6. Authentification

Méthodes supportées :

- OAuth2
- OpenID Connect
- JWT
- API Key
- SSO institutionnel

Les tokens sont validés avant toute requête.

---

# 7. Autorisation

Contrôle basé sur les rôles (RBAC).

Exemples :

- Ministre
- DRENA
- Inspection
- Proviseur
- Censeur
- Enseignant
- Élève
- Parent

Chaque requête est vérifiée.

---

# 8. Routage

Exemples :

```text
/api/planner/*
        │
Planning Service

/api/governance/*
        │
Governance Service

/api/family/*
        │
Family Service

/api/booking/*
        │
Booking Service
```

Les routes sont versionnées.

---

# 9. Versionnement

Convention :

```text
/api/v1/...

/api/v2/...
```

Les anciennes versions restent compatibles pendant la période de transition.

---

# 10. Gestion des erreurs

Format unique :

```json
{
  "success": false,
  "code": "PLN-404",
  "message": "Planning introuvable",
  "timestamp": "2026-07-01T10:30:00Z"
}
```

Toutes les erreurs suivent ce modèle.

---

# 11. Limitation de débit (Rate Limiting)

Objectifs :

- éviter les abus ;
- protéger les services ;
- limiter les attaques.

Exemple :

```text
100 requêtes/minute

par utilisateur

1000 requêtes/minute

par établissement
```

---

# 12. Cache

Les ressources peu volatiles peuvent être mises en cache :

- référentiels ;
- disciplines ;
- niveaux ;
- régions ;
- établissements.

Redis est recommandé.

---

# 13. Journalisation

Chaque requête génère un journal :

- utilisateur ;
- établissement ;
- adresse IP ;
- durée ;
- statut ;
- identifiant de corrélation.

Les journaux alimentent le système d'audit.

---

# 14. Sécurité

Mesures :

- HTTPS obligatoire ;
- HSTS ;
- CORS contrôlé ;
- protection CSRF ;
- protection XSS ;
- validation des entrées ;
- limitation des tailles de requêtes ;
- blocage automatique des IP malveillantes.

---

# 15. Webhooks

Les systèmes externes peuvent être notifiés.

Exemples :

- abonnement validé ;
- emploi du temps publié ;
- paiement reçu ;
- nouvel établissement.

Chaque webhook est signé.

---

# 16. Monitoring

Indicateurs :

- nombre de requêtes ;
- latence moyenne ;
- erreurs 4xx ;
- erreurs 5xx ;
- temps de réponse ;
- disponibilité.

Prometheus et Grafana sont recommandés.

---

# 17. Haute disponibilité

Architecture :

```text
          Load Balancer
                │
      ┌─────────┴─────────┐
      ▼                   ▼
API Gateway 1      API Gateway 2
      │                   │
      └─────────┬─────────┘
                ▼
        Microservices EduWeb
```

La Gateway ne doit jamais constituer un point de défaillance unique.

---

# 18. Checklist

- □ HTTPS activé
- □ JWT validés
- □ RBAC appliqué
- □ Versionnement défini
- □ Rate limiting actif
- □ Cache configuré
- □ Monitoring opérationnel
- □ Journalisation complète
- □ Webhooks sécurisés
- □ Haute disponibilité validée
