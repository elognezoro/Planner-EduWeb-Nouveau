# 1. Vision

EduWeb Planner est construit selon une architecture **Domain Driven Design (DDD)** où chaque domaine métier est implémenté sous forme de microservice autonome.

Chaque microservice possède :

- sa logique métier ;
- ses API ;
- ses événements ;
- sa persistance ;
- son cycle de vie.

L'objectif est de permettre l'évolution indépendante de chaque domaine sans impacter les autres.

---

# 2. Pourquoi les microservices ?

Une architecture monolithique devient rapidement difficile à maintenir lorsque :

- plusieurs équipes travaillent simultanément ;
- plusieurs pays utilisent la plateforme ;
- les fonctionnalités augmentent rapidement ;
- les besoins de montée en charge diffèrent selon les modules.

Les microservices permettent :

- un développement parallèle ;
- des déploiements indépendants ;
- une meilleure résilience ;
- une meilleure scalabilité ;
- une évolution progressive.

---

# 3. Principes

## Domaine métier

Un microservice = un domaine métier.

---

## Indépendance

Chaque service peut être déployé séparément.

---

## Faible couplage

Les services ne partagent pas directement leurs données.

---

## API First

Toute communication passe par des API ou des événements.

---

## Ownership

Chaque équipe est responsable de son microservice.

# 8. Persistance

Principe fondamental :

> **Database per Service**

Chaque microservice possède sa propre base logique.

Exemple :

```text
Teacher DB

Student DB

Planning DB

Notification DB

Analytics DB
```

Aucun accès direct entre bases.

---

# 9. Transactions

Les transactions distribuées sont évitées.

Approche recommandée :

Saga Pattern.

```text
Créer établissement

↓

Créer utilisateurs

↓

Créer classes

↓

Créer salles

↓

Publier événement
```

En cas d'échec :

compensation automatique.

---

# 10. Résilience

Chaque service implémente :

- Retry
- Timeout
- Circuit Breaker
- Bulkhead
- Health Check

Les pannes locales ne doivent jamais arrêter toute la plateforme.

---

# 11. Déploiement

Chaque service est empaqueté sous Docker.

```text
Docker Image

↓

Registry

↓

Kubernetes

↓

Pods

↓

Service

↓

Ingress
```

Les déploiements sont indépendants.

---

# 12. Monitoring

Chaque microservice expose :

- métriques Prometheus
- logs structurés
- traces OpenTelemetry

Visualisation :

- Grafana
- Jaeger

---

# 13. Sécurité

Chaque service applique :

- JWT
- RBAC
- validation des entrées
- chiffrement TLS
- audit
- gestion des secrets

Les secrets sont stockés dans :

- Vault
- Kubernetes Secrets

---

# 14. Scalabilité

Chaque microservice peut être répliqué.

Exemple :

```text
Timetable Service

Pod 1

Pod 2

Pod 3

Pod 4
```

Le Scheduler pourra disposer d'un cluster dédié pendant les périodes de rentrée scolaire.

---

# 15. Gouvernance

Chaque microservice possède :

- un propriétaire ;
- une documentation ;
- un contrat OpenAPI ;
- une politique de versionnement ;
- des tests automatisés ;
- des SLA.

Les changements majeurs doivent être validés par l'Architecture Board.
