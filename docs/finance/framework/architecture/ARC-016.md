# ARC-016 — Architecture des Communications et des API

> **Objectif :** Définir l'architecture des communications internes et externes d'EduWeb Planner afin d'assurer des échanges fiables, sécurisés, performants et interopérables entre tous les composants de l'écosystème.

# 1. Vision

Toutes les communications de la plateforme EduWeb Planner reposent sur une approche **API First**.

Chaque fonctionnalité est exposée comme un service réutilisable pouvant être consommé par :

- les applications Web ;
- les applications mobiles ;
- les partenaires institutionnels ;
- les ministères ;
- les plateformes EduWeb ;
- les services d'Intelligence Artificielle.

Les API constituent le contrat officiel entre les différents domaines fonctionnels.

---

# 2. Objectifs

L'architecture doit permettre :

- une communication standardisée ;
- une forte interopérabilité ;
- une faible dépendance entre services ;
- une évolutivité indépendante ;
- une sécurité homogène ;
- une supervision centralisée.

---

# 3. Principes d'architecture

Les échanges reposent sur les principes suivants :

- API First
- Contract First
- Loose Coupling
- Event Driven
- Secure by Default
- Backward Compatibility
- Idempotence
- Stateless Services

# 5. Architecture API First

Chaque domaine fonctionnel possède sa propre API.

Exemples :

| Domaine | API |
|----------|----------------------------|
| Utilisateurs | Identity API |
| Établissements | School API |
| Enseignants | Teacher API |
| Élèves | Student API |
| Emplois du temps | Scheduler API |
| Examens | Assessment API |
| Notifications | Notification API |
| IA | AI Gateway API |

Chaque API est indépendante et documentée.

---

# 6. Communication synchrone

Les communications synchrones utilisent principalement :

## REST

Utilisé pour :

- CRUD
- consultation
- administration
- configuration

---

## GraphQL

Utilisé lorsque :

- plusieurs ressources doivent être agrégées ;
- les clients mobiles souhaitent limiter les volumes échangés ;
- les tableaux de bord nécessitent des requêtes complexes.

---

## gRPC

Utilisé pour :

- communications internes haute performance ;
- échanges entre microservices ;
- traitements IA.

---

# 7. Communication asynchrone

Les traitements longs utilisent une architecture événementielle.

Exemples :

- génération d'un emploi du temps ;
- envoi de milliers de notifications ;
- calcul des statistiques nationales ;
- export massif.

Technologies recommandées :

- RabbitMQ
- Apache Kafka
- Redis Streams
- NATS

---

# 8. Architecture événementielle

Exemple :

```text
Nouvel enseignant créé

↓

TeacherCreated

↓

Message Broker

↓

Scheduler Service

↓

Notification Service

↓

Analytics Service

↓

Audit Service
```

Chaque consommateur travaille indépendamment.

---

# 9. Gouvernance des API

Toutes les API possèdent :

- un propriétaire ;
- une documentation OpenAPI ;
- une politique de sécurité ;
- un cycle de vie ;
- une stratégie de versionnement ;
- des tests automatisés.

Une revue d'architecture est obligatoire avant la publication d'une nouvelle API.

---

# 10. Sécurité

Les communications sont protégées par :

- HTTPS obligatoire ;
- TLS 1.3 ;
- OAuth2 ;
- OpenID Connect ;
- JWT ;
- MFA pour les opérations sensibles ;
- chiffrement des secrets.

Les API sont protégées par :

- limitation de débit (Rate Limiting) ;
- quotas ;
- filtrage IP ;
- validation des jetons ;
- journalisation.

---

# 11. Versionnement

Convention retenue :

```text
/api/v1/

/api/v2/

/api/v3/
```

Les anciennes versions restent maintenues pendant une période de transition définie par la gouvernance.

Les évolutions incompatibles nécessitent une nouvelle version majeure.

---

# 12. Performance

Objectifs :

| Indicateur | Cible |
|------------|-------:|
| Temps moyen REST | < 300 ms |
| Temps moyen GraphQL | < 500 ms |
| Temps gRPC | < 100 ms |
| Disponibilité API | ≥ 99,9 % |

Optimisations :

- cache Redis ;
- compression HTTP ;
- pagination ;
- requêtes optimisées ;
- CDN pour les ressources statiques.

---

# 13. Résilience

Les API intègrent :

- Retry automatique ;
- Circuit Breaker ;
- Timeout configurable ;
- Bulkhead Pattern ;
- Fallback Service ;
- File d'attente en cas d'indisponibilité.

Les erreurs sont normalisées.

Exemple :

```json
{
  "timestamp": "...",
  "status": 404,
  "code": "RESOURCE_NOT_FOUND",
  "message": "Teacher not found",
  "traceId": "..."
}
```

---

# 14. Observabilité

Chaque appel API produit :

- métriques ;
- traces distribuées ;
- journaux ;
- identifiant de corrélation (Correlation ID).

Outils recommandés :

- Prometheus
- Grafana
- Jaeger
- Loki
- OpenTelemetry

Les indicateurs suivants sont suivis :

- nombre d'appels ;
- temps de réponse ;
- taux d'erreur ;
- disponibilité ;
- consommation par client.

# Conclusion

L'architecture des communications et des API constitue le système nerveux d'EduWeb Planner. Fondée sur une approche **API First**, **Event Driven** et **Cloud Native**, elle garantit une communication sécurisée, performante et évolutive entre les microservices, les applications clientes, les plateformes EduWeb et les systèmes institutionnels. Cette architecture favorise l'interopérabilité, la réutilisabilité des services et l'ouverture progressive de l'écosystème à de nouveaux partenaires.
