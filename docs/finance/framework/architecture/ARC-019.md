# ARC-019 — Architecture de Résilience, Observabilité et Site Reliability Engineering (SRE)

> **Objectif :** Définir l'architecture de résilience et d'observabilité d'EduWeb Planner afin de garantir une disponibilité élevée, une détection précoce des incidents, une amélioration continue de la fiabilité et une exploitation conforme aux principes du Site Reliability Engineering (SRE).

# 1. Vision

EduWeb Planner est une plateforme critique pouvant être utilisée simultanément par :

- plusieurs ministères ;
- plusieurs DRENA ;
- plusieurs inspections ;
- plusieurs milliers d'établissements ;
- plusieurs millions d'utilisateurs.

L'objectif est de garantir un service disponible, stable et mesurable, même en cas de panne d'un composant ou d'un site entier.

---

# 2. Objectifs

L'architecture doit permettre :

- une disponibilité supérieure à **99,9 %** ;
- une détection proactive des incidents ;
- une réduction du temps moyen de résolution (MTTR) ;
- une surveillance continue des performances ;
- une amélioration permanente de la fiabilité.

---

# 3. Principes SRE

EduWeb Planner adopte les principes du **Site Reliability Engineering** :

- Automatisation des opérations répétitives ;
- Mesure continue de la fiabilité ;
- Culture post-mortem sans recherche de culpabilité (*Blameless Postmortem*) ;
- Gestion du budget d'erreur (*Error Budget*) ;
- Amélioration continue.

---

# 4. Architecture de résilience

```text
                  Utilisateurs

                         │

                  Load Balancer

                         │

                Kubernetes Cluster

         ┌────────────┴─────────────┐

         ▼                          ▼

 Service A                    Service B

         ▼                          ▼

 PostgreSQL Cluster      Redis Cluster

         └────────────┬─────────────┘

                      ▼

          Sauvegardes & Réplication
```

Les mécanismes de résilience comprennent :

- réplication ;
- bascule automatique (*Failover*) ;
- redémarrage automatique des services ;
- équilibrage de charge ;
- reprise automatique des Pods.

---

# 5. Architecture d'observabilité

L'observabilité repose sur trois piliers.

## 5.1 Métriques

Exemples :

- CPU ;
- mémoire ;
- latence ;
- disponibilité ;
- nombre de connexions ;
- erreurs HTTP ;
- saturation des files d'attente.

---

## 5.2 Journaux (Logs)

Tous les composants produisent des journaux structurés.

Les journaux sont centralisés dans une plateforme unique.

Exemples :

- authentification ;
- erreurs applicatives ;
- appels API ;
- événements métiers.

---

## 5.3 Traces distribuées

Chaque requête reçoit un **Correlation ID** permettant de suivre son parcours à travers les microservices.

---

# 6. Gestion des incidents

Le cycle de traitement est le suivant :

```text
Détection

↓

Qualification

↓

Priorisation

↓

Affectation

↓

Correction

↓

Validation

↓

Post-Mortem

↓

Capitalisation
```

Chaque incident critique fait l'objet d'un rapport d'analyse.

---

# 7. Gestion des erreurs

Les erreurs sont classées selon leur criticité.

| Niveau | Exemple |
|---------|----------|
| P1 | Plateforme indisponible |
| P2 | Fonction critique dégradée |
| P3 | Fonction secondaire indisponible |
| P4 | Anomalie mineure |

Des procédures d'escalade sont définies pour chaque niveau.

---

# 8. SLI, SLO et SLA

## Service Level Indicators (SLI)

Indicateurs mesurés :

- disponibilité ;
- temps de réponse ;
- taux d'erreur ;
- débit ;
- succès des sauvegardes.

---

## Service Level Objectives (SLO)

Exemples :

| Indicateur | Objectif |
|------------|----------:|
| Disponibilité | ≥ 99,9 % |
| Temps de réponse API | < 300 ms |
| Génération d'un emploi du temps | < 2 min |
| Taux d'erreur HTTP | < 0,5 % |

---

## Service Level Agreements (SLA)

Les engagements de service sont établis selon les catégories d'utilisateurs :

- établissements ;
- académies ;
- ministères ;
- partenaires.

---

# 9. Capacity Planning

Les ressources sont dimensionnées à partir :

- du nombre d'utilisateurs ;
- du nombre d'établissements ;
- du nombre de requêtes ;
- de la consommation historique.

Les prévisions sont revues régulièrement afin d'anticiper les besoins.

---

# 10. Chaos Engineering

Des tests contrôlés sont réalisés afin de vérifier la résilience de la plateforme.

Exemples :

- arrêt volontaire d'un Pod ;
- coupure réseau simulée ;
- perte d'un nœud Kubernetes ;
- indisponibilité d'une base de données secondaire.

Les résultats permettent d'améliorer la robustesse de l'infrastructure.

---

# 11. Astreinte et exploitation

Une organisation d'astreinte est mise en place.

Les équipes disposent :

- de tableaux de bord temps réel ;
- d'alertes automatiques ;
- de procédures d'intervention ;
- d'une base de connaissances.

Les interventions sont historisées.

---

# 12. Amélioration continue

Chaque incident donne lieu à :

- une analyse des causes profondes (*Root Cause Analysis*) ;
- un plan d'actions correctives ;
- une mise à jour de la documentation ;
- une automatisation lorsque cela est pertinent.

Les indicateurs de fiabilité sont suivis dans le temps.

# Conclusion

L'architecture de résilience, d'observabilité et de Site Reliability Engineering d'EduWeb Planner garantit une plateforme capable de résister aux défaillances, de détecter rapidement les anomalies et d'améliorer continuellement sa fiabilité. En combinant supervision, automatisation, métriques, journalisation, traçabilité et pratiques SRE, EduWeb Planner se dote d'un cadre d'exploitation conforme aux standards des plateformes critiques modernes.
