# ARC-007 — Architecture Haute Disponibilité (High Availability)

> **Objectif :** Définir l'architecture garantissant la continuité de service d'EduWeb Planner malgré les pannes matérielles, logicielles ou réseau.

# 1. Vision

EduWeb Planner est destiné à être utilisé par :

- des milliers d'établissements ;
- des centaines de milliers d'enseignants ;
- plusieurs millions d'élèves.

Une interruption de service peut avoir un impact national.

La plateforme doit donc être conçue pour fonctionner **24h/24 et 7j/7**, avec un objectif de disponibilité de **99,9 %** à **99,99 %** selon les composants.

---

# 2. Objectifs

L'architecture HA vise à :

- éviter les points uniques de défaillance ;
- garantir la continuité de service ;
- assurer une reprise automatique ;
- permettre les mises à jour sans interruption ;
- maintenir les performances en cas de forte charge.

---

# 3. Exigences

| Élément | Objectif |
|----------|----------|
| Disponibilité | ≥ 99,9 % |
| RTO (Recovery Time Objective) | < 30 minutes |
| RPO (Recovery Point Objective) | < 5 minutes |
| Scalabilité | Horizontale |
| Mises à jour | Sans interruption (Rolling Update) |

---

# 5. Redondance

Les composants critiques doivent être dupliqués :

- API Gateway ;
- Microservices ;
- Bases de données ;
- Cache Redis ;
- Message Broker ;
- Stockage objet.

Aucun composant ne doit constituer un **Single Point of Failure (SPOF)**.

---

# 6. Répartition de charge

Le trafic est réparti via un **Load Balancer**.

Stratégies possibles :

- Round Robin ;
- Least Connections ;
- IP Hash ;
- Weighted Load Balancing.

Pour EduWeb Planner, **Least Connections** est recommandé pour les services applicatifs.

---

# 7. Tolérance aux pannes

Les microservices doivent implémenter :

- Health Checks (`/health`) ;
- Readiness Probes ;
- Liveness Probes ;
- Circuit Breaker ;
- Retry ;
- Timeout ;
- Bulkhead Pattern.

En cas de panne, Kubernetes redémarre automatiquement les pods défaillants.

---

# 8. Haute disponibilité des bases de données

Architecture recommandée :

```text
          PostgreSQL Primary
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 PostgreSQL Replica   PostgreSQL Replica
```

Fonctionnalités :

- réplication synchrone ou asynchrone ;
- bascule automatique (Failover) ;
- sauvegardes continues (WAL).

---

# 9. Haute disponibilité Kubernetes

Le cluster doit comporter :

- plusieurs nœuds maîtres (si possible) ;
- plusieurs nœuds workers ;
- autoscaling horizontal (HPA) ;
- autoscaling du cluster.

Les déploiements utilisent des **Rolling Updates** afin d'éviter toute interruption de service.

---

# 10. Sauvegardes

Politique recommandée :

- Sauvegarde incrémentielle toutes les heures ;
- Sauvegarde complète quotidienne ;
- Conservation 30 jours ;
- Réplication sur un site secondaire.

Les sauvegardes doivent être régulièrement restaurées en environnement de test pour vérifier leur intégrité.

---

# 11. Monitoring

Outils recommandés :

- Prometheus ;
- Grafana ;
- Alertmanager ;
- Loki (logs) ;
- Jaeger (traces).

Indicateurs suivis :

- disponibilité ;
- CPU ;
- mémoire ;
- latence ;
- erreurs HTTP ;
- temps de réponse des bases de données.

---

# 12. Reprise automatique

En cas de défaillance :

1. Détection automatique ;
2. Isolation du composant ;
3. Redémarrage ;
4. Bascule si nécessaire ;
5. Notification des administrateurs ;
6. Journalisation de l'incident.

---

# 13. SLA

| Service | SLA cible |
|----------|-----------|
| Authentification | 99,99 % |
| Génération des emplois du temps | 99,9 % |
| Notifications | 99,5 % |
| Reporting | 99,5 % |
| API Gateway | 99,99 % |

---

# 14. Checklist

- □ Aucun SPOF identifié
- □ Réplication des bases configurée
- □ Load Balancer opérationnel
- □ Rolling Updates activés
- □ Sauvegardes automatisées
- □ Tests de restauration réalisés
- □ Monitoring complet
- □ Alertes configurées
- □ SLA documentés
- □ Procédures de reprise validées
