# ARC-017 — Architecture Kubernetes et Orchestration

> **Objectif :** Définir l'architecture d'orchestration des conteneurs d'EduWeb Planner afin d'assurer une exécution hautement disponible, évolutive, automatisée et résiliente de l'ensemble des services applicatifs.

# 1. Vision

Kubernetes constitue la plateforme standard d'orchestration d'EduWeb Planner.

Il permet :

- l'automatisation des déploiements ;
- la haute disponibilité ;
- l'équilibrage automatique des charges ;
- l'auto-réparation des services ;
- la montée en charge horizontale.

L'ensemble des microservices de la plateforme est conçu pour fonctionner dans un environnement Kubernetes.

---

# 2. Objectifs

L'architecture Kubernetes vise à :

- standardiser l'exécution des services ;
- réduire les interruptions de service ;
- faciliter les mises à jour ;
- améliorer l'élasticité ;
- simplifier l'exploitation.

---

# 3. Principes

L'architecture repose sur les principes suivants :

- Cloud Native
- Immutable Infrastructure
- Infrastructure as Code
- GitOps
- Self-Healing
- Declarative Configuration
- High Availability

# 5. Architecture des clusters

Selon la taille du déploiement :

## Petit déploiement

- 3 nœuds

---

## Déploiement régional

- 5 à 8 nœuds

---

## Déploiement national

- 15 à 50 nœuds

---

## Déploiement multi-pays

Plusieurs clusters interconnectés.

Exemple :

```text
Cluster Côte d'Ivoire

Cluster Sénégal

Cluster Bénin

Cluster Cameroun

Cluster RDC
```

Chaque cluster peut fonctionner de manière autonome tout en participant à un écosystème fédéré.

---

# 6. Organisation des namespaces

Chaque domaine fonctionnel dispose de son propre namespace.

Exemple :

```text
eduweb-system

identity

schools

teachers

students

scheduler

planning-ai

analytics

notification

monitoring

logging

security
```

Cette organisation facilite :

- l'isolation ;
- les quotas ;
- la sécurité ;
- la supervision.

---

# 7. Déploiement des applications

Les applications sont déployées via :

- Deployments ;
- StatefulSets ;
- DaemonSets ;
- Jobs ;
- CronJobs.

Les mises à jour utilisent :

- Rolling Updates ;
- Blue/Green Deployment ;
- Canary Deployment.

Les images sont versionnées et stockées dans un registre privé.

---

# 8. Réseau Kubernetes

Le réseau est assuré par un plugin CNI compatible Kubernetes.

Fonctionnalités :

- communication Pod à Pod ;
- politiques réseau (Network Policies) ;
- services ClusterIP, NodePort et LoadBalancer ;
- Ingress Controller.

Toutes les communications sont chiffrées.

---

# 9. Stockage persistant

Les données persistantes utilisent des Persistent Volumes (PV) et Persistent Volume Claims (PVC).

Exemples :

| Service | Type de stockage |
|----------|------------------|
| PostgreSQL | Volume persistant SSD |
| Redis | Volume persistant |
| MinIO | Stockage objet |
| Logs | Volume partagé |

Les classes de stockage sont adaptées aux performances requises.

---

# 10. Haute disponibilité

Les composants critiques sont répliqués.

Exemple :

| Composant | Réplicas minimum |
|------------|-----------------:|
| API Gateway | 3 |
| Scheduler | 3 |
| Identity | 3 |
| Notification | 2 |
| AI Gateway | 2 |

Les sondes Kubernetes (Liveness et Readiness) garantissent la disponibilité des services.

---

# 11. Autoscaling

L'architecture supporte :

- Horizontal Pod Autoscaler (HPA) ;
- Vertical Pod Autoscaler (VPA) ;
- Cluster Autoscaler.

Critères possibles :

- CPU ;
- mémoire ;
- nombre de requêtes ;
- files d'attente ;
- métriques métier.

---

# 12. Sécurité

Les mesures appliquées comprennent :

- RBAC Kubernetes ;
- Secrets chiffrés ;
- Network Policies ;
- Pod Security Standards ;
- Admission Controllers ;
- signatures des images ;
- analyse des vulnérabilités avant déploiement.

Les conteneurs s'exécutent sans privilèges lorsque cela est possible.

---

# 13. Observabilité

L'infrastructure est supervisée grâce à :

- Prometheus ;
- Grafana ;
- Loki ;
- Jaeger ;
- OpenTelemetry.

Les métriques collectées incluent :

- disponibilité des Pods ;
- consommation CPU ;
- mémoire ;
- temps de réponse ;
- redémarrages ;
- saturation des ressources.

Des alertes sont configurées pour les incidents critiques.

---

# 14. GitOps

Les déploiements sont pilotés selon une approche GitOps.

Principe :

```text
Git Repository

↓

Validation

↓

Argo CD / Flux

↓

Cluster Kubernetes
```

Toute modification de configuration passe par une Pull Request et laisse une trace complète.

---

# 15. Continuité d'activité

Les clusters sont conçus pour :

- supporter la perte d'un nœud ;
- redémarrer automatiquement les Pods ;
- répartir les charges entre zones de disponibilité ;
- restaurer les applications après incident.

Les sauvegardes des configurations Kubernetes sont automatisées.

# Conclusion

L'architecture Kubernetes d'EduWeb Planner fournit une plateforme d'orchestration moderne, résiliente et automatisée pour l'ensemble des services de l'écosystème. Grâce à Kubernetes, à GitOps et à l'observabilité native, la plateforme est en mesure de supporter un déploiement progressif, depuis un établissement unique jusqu'à un environnement multi-pays à l'échelle continentale, tout en garantissant disponibilité, sécurité et évolutivité.
