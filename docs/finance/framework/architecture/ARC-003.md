# ARC-003 — Architecture événementielle

> **Objectif :** Définir l'architecture événementielle (Event-Driven Architecture – EDA) d'EduWeb Planner afin de découpler les services, d'améliorer les performances, de faciliter l'intégration et d'assurer la scalabilité de la plateforme.

# 1. Vision

L'architecture événementielle permet aux différents modules d'EduWeb Planner de communiquer sans dépendances directes.

Chaque module publie des événements lorsqu'une action importante survient.

Les autres modules peuvent réagir à ces événements sans modifier le service d'origine.

---

# 2. Pourquoi une architecture événementielle ?

Dans une architecture classique :

```text
Module A
   │
   ▼
Module B
   │
   ▼
Module C
```

Chaque module dépend du précédent.

Dans une architecture événementielle :

```text
Module A
   │
Publie un événement
   │
════════════════════════════
        Event Bus
════════════════════════════
   │      │       │
   ▼      ▼       ▼
Module B Module C Module D
```

Les services deviennent indépendants.

---

# 3. Principes

## Découplage

Les modules ne s'appellent pas directement.

Ils échangent uniquement des événements.

---

## Asynchronisme

Les traitements longs sont exécutés en arrière-plan.

---

## Résilience

Une panne d'un consommateur n'empêche pas la publication d'un événement.

---

## Traçabilité

Tous les événements sont journalisés.

---

## Rejouabilité

Les événements peuvent être rejoués pour reconstruire un état.

# 6. Producteurs d'événements

Les principaux producteurs sont :

- Gestion des utilisateurs
- Gestion des établissements
- Générateur d'emplois du temps
- Examens
- Paiements
- Notifications
- IA

Chaque service est responsable de la publication de ses propres événements.

---

# 7. Consommateurs

Les événements peuvent être consommés par :

- le moteur IA ;
- le module de statistiques ;
- le système d'audit ;
- les notifications ;
- les tableaux de bord ;
- les connecteurs externes.

---

# 8. Bus d'événements

Solutions envisageables :

- RabbitMQ
- Apache Kafka
- NATS
- Redis Streams

Pour EduWeb Planner :

- RabbitMQ : simplicité de mise en œuvre ;
- Kafka : très forte volumétrie ;
- NATS : faible latence.

Le choix dépendra de la taille du déploiement.

---

# 9. Structure d'un événement

Exemple JSON :

```json
{
  "eventId": "evt-000145",
  "type": "ScheduleGenerated",
  "timestamp": "2026-08-01T10:35:00Z",
  "tenantId": "CI-DRENA-ABJ",
  "schoolId": "LMA001",
  "payload": {
    "scheduleId": "EDT-2026-001",
    "status": "SUCCESS"
  }
}
```

Chaque événement comporte :

- identifiant unique ;
- type ;
- horodatage ;
- contexte multi-tenant ;
- données métier.

# 11. Sécurité

Les événements doivent être :

- authentifiés ;
- horodatés ;
- chiffrés si nécessaire ;
- signés dans les cas sensibles.

Aucun événement ne doit contenir de mot de passe ou de données confidentielles non protégées.

---

# 12. Performance

Objectifs :

- latence faible ;
- traitement parallèle ;
- reprise automatique ;
- équilibrage de charge ;
- files persistantes.

---

# 13. Gouvernance

Chaque événement doit disposer :

- d'un propriétaire ;
- d'une documentation ;
- d'une version ;
- d'un contrat (schema) ;
- d'une politique de rétention.

Les évolutions doivent être rétrocompatibles autant que possible.

---

# 14. Checklist

- □ Tous les événements sont documentés.
- □ Les producteurs sont identifiés.
- □ Les consommateurs sont connus.
- □ Les schémas sont versionnés.
- □ Les traitements sont idempotents.
- □ Les événements sont journalisés.
- □ Les erreurs sont rejouables.
- □ Les files sont surveillées.
- □ Les performances sont mesurées.
- □ Les données sensibles sont protégées.
