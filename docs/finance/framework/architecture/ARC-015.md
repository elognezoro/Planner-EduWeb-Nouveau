# ARC-015 — Architecture Infrastructure

> **Objectif :** Définir l'architecture d'infrastructure d'EduWeb Planner afin de fournir une plateforme robuste, hautement disponible, sécurisée, évolutive et capable de supporter un déploiement national et international.

# 1. Vision

L'infrastructure d'EduWeb Planner constitue le socle technique de l'ensemble de la plateforme.

Elle doit permettre :

- une disponibilité permanente ;
- une montée en charge progressive ;
- une exploitation simplifiée ;
- une automatisation maximale ;
- une résilience face aux incidents.

Elle est conçue selon une approche **Cloud Native**, tout en restant compatible avec un déploiement **On-Premise** lorsque les contraintes réglementaires ou institutionnelles l'exigent.

---

# 2. Objectifs

L'infrastructure doit garantir :

- une disponibilité ≥ 99,9 % ;
- un temps de réponse inférieur à 300 ms pour les opérations courantes ;
- un déploiement automatisé ;
- une reprise rapide après incident ;
- une évolutivité horizontale.

---

# 3. Principes

Les principes retenus sont :

- Infrastructure as Code (IaC)
- Cloud Native
- Immutable Infrastructure
- High Availability
- Scalability
- Observability
- Zero Trust Network

# 5. Couche Cloud

L'infrastructure peut être déployée sur :

## Cloud public

- AWS
- Microsoft Azure
- Google Cloud Platform
- OVHcloud
- Oracle Cloud

---

## Cloud privé

- VMware
- OpenStack
- Proxmox VE

---

## Cloud hybride

Le modèle recommandé combine :

- applications critiques hébergées sur un cloud privé ou souverain ;
- services publics, analytiques ou IA déployés sur un cloud public.

---

# 6. Couche Réseau

L'architecture réseau comprend :

- pare-feu de nouvelle génération ;
- segmentation VLAN ;
- VPN d'administration ;
- DNS sécurisé ;
- équilibrage de charge (Load Balancer) ;
- passerelle API.

Toutes les communications interservices utilisent TLS.

---

# 7. Couche Calcul (Compute)

Les services sont exécutés dans des conteneurs orchestrés par Kubernetes.

Chaque nœud dispose :

- d'un système Linux sécurisé ;
- d'un moteur de conteneurs ;
- d'agents de supervision.

Le dimensionnement est ajusté automatiquement selon la charge (Horizontal Pod Autoscaler).

---

# 8. Couche Stockage

Le stockage est réparti en plusieurs catégories :

| Type | Usage |
|------|-------|
| Bloc | Bases de données |
| Objet | Documents, pièces jointes |
| Fichier | Sauvegardes, journaux |
| Cache | Redis |

Les documents sont stockés dans un stockage objet compatible S3 (MinIO ou équivalent).

---

# 9. Couche Données

Les composants principaux sont :

- PostgreSQL en cluster ;
- Redis pour le cache et les files d'attente légères ;
- stockage objet pour les fichiers ;
- Data Warehouse pour l'analytique.

La réplication est activée entre plusieurs nœuds.

---

# 10. Couche Conteneurs

Tous les services applicatifs sont empaquetés sous forme d'images Docker.

Fonctionnalités :

- orchestration Kubernetes ;
- autoscaling ;
- rolling updates ;
- blue/green deployment ;
- canary deployment (selon les besoins).

Les images sont stockées dans un registre privé.

---

# 11. Haute disponibilité

Les composants critiques sont redondés :

- Load Balancer ;
- API Gateway ;
- nœuds Kubernetes ;
- PostgreSQL ;
- Redis ;
- stockage.

En cas de panne d'un composant, le trafic est automatiquement redirigé.

---

# 12. Sauvegardes

La politique de sauvegarde comprend :

- sauvegardes incrémentielles horaires ;
- sauvegardes complètes quotidiennes ;
- archivage hebdomadaire ;
- réplication hors site.

Des tests de restauration sont réalisés régulièrement afin de vérifier l'intégrité des sauvegardes.

---

# 13. Supervision

L'observabilité repose sur plusieurs niveaux :

## Infrastructure

- CPU ;
- mémoire ;
- disque ;
- réseau.

## Applications

- disponibilité ;
- temps de réponse ;
- erreurs.

## Base de données

- requêtes lentes ;
- connexions ;
- réplication.

## Sécurité

- connexions suspectes ;
- alertes ;
- tentatives d'intrusion.

Outils recommandés :

- Prometheus ;
- Grafana ;
- Loki ;
- Alertmanager ;
- Jaeger.

---

# 14. Capacité et montée en charge

L'infrastructure est conçue pour évoluer progressivement.

### Capacité initiale

- quelques dizaines d'établissements ;
- plusieurs milliers d'utilisateurs.

### Capacité cible

- plusieurs milliers d'établissements ;
- plusieurs millions d'utilisateurs ;
- plusieurs centaines de milliers de connexions quotidiennes.

La montée en charge est principalement horizontale.

---

# 15. Gestion des environnements

Les environnements sont isolés :

| Environnement | Finalité |
|--------------|----------|
| Développement | Création des fonctionnalités |
| Intégration | Tests techniques |
| Validation | Recette fonctionnelle |
| Préproduction | Simulation de production |
| Production | Exploitation |

Chaque environnement dispose :

- de sa configuration ;
- de ses secrets ;
- de ses bases de données ;
- de son monitoring.

# Conclusion

L'architecture d'infrastructure d'EduWeb Planner fournit une fondation technique moderne, résiliente et évolutive. Grâce à une approche Cloud Native, à l'orchestration par Kubernetes, à une supervision complète et à une haute disponibilité native, elle permet de soutenir durablement le déploiement de la plateforme à l'échelle des établissements, des académies et des ministères, tout en garantissant performance, sécurité et continuité de service.
