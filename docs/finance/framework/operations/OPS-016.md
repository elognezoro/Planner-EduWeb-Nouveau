# 1. Introduction

Le développement moderne ne peut plus séparer :

- le développement ;
- l'exploitation ;
- la cybersécurité ;
- la qualité ;
- la conformité.

Historiquement, ces disciplines étaient exécutées de manière séquentielle :

```text
Développement

↓

Tests

↓

Livraison

↓

Sécurité

↓

Production
```

Cette approche générait :

- des délais importants ;
- des conflits entre équipes ;
- des vulnérabilités découvertes trop tard ;
- des déploiements risqués ;
- une faible fréquence de livraison.

Le DevSecOps transforme cette approche en intégrant toutes ces activités dans un pipeline automatisé.

```text
Developer

+

Security

+

Operations

+

Automation

=

Continuous Delivery
```

---

# 2. Vision

EduWeb adopte un modèle DevSecOps où :

- la sécurité est intégrée dès la conception ;
- les contrôles sont automatisés ;
- les infrastructures sont décrites comme du code ;
- les environnements sont reproductibles ;
- les déploiements sont traçables ;
- les politiques sont versionnées ;
- les pipelines deviennent la colonne vertébrale opérationnelle.

---

# 3. Objectifs

Le DevSecOps poursuit notamment les objectifs suivants :

- accélérer les livraisons ;
- réduire les erreurs humaines ;
- intégrer la sécurité dès le développement ;
- automatiser les contrôles ;
- améliorer la qualité logicielle ;
- renforcer la traçabilité ;
- faciliter les audits ;
- réduire les temps de restauration ;
- améliorer la résilience ;
- soutenir les pratiques GitOps et SRE.

# 10. Gouvernance du code source

Le code doit être :

- versionné ;
- relu ;
- signé lorsque nécessaire ;
- documenté ;
- traçable.

Les dépôts doivent être protégés.

# 11. Gestion des branches

Exemple :

```text
main

├── develop

├── feature/*

├── release/*

└── hotfix/*
```

Les règles de fusion imposent :

- revue de code ;
- validation CI ;
- tests réussis ;
- absence de vulnérabilité critique.

# 12. Intégration Continue (CI)

La CI automatise :

- compilation ;
- packaging ;
- tests ;
- analyses ;
- génération de rapports.

Chaque commit déclenche automatiquement le pipeline.

---

# 13. Livraison Continue (CD)

Le pipeline prépare les artefacts pour la production.

Les promotions entre environnements sont contrôlées.

---

# 14. Déploiement Continu

Lorsque le risque est acceptable :

```text
Commit validé

↓

Déploiement automatique

↓

Validation

↓

Surveillance
```

Pour les systèmes critiques, une validation humaine peut rester obligatoire.

# 15. Infrastructure as Code

Les infrastructures sont décrites sous forme de fichiers versionnés.

Exemples :

- Kubernetes YAML ;
- Terraform ;
- Ansible.

Avantages :

- reproductibilité ;
- audit ;
- rollback ;
- automatisation.

---

# 16. Configuration as Code

Les configurations doivent être :

- versionnées ;
- séparées du code ;
- reproductibles ;
- auditables.

---

# 17. Policy as Code

Les politiques de sécurité sont codées.

Exemples :

- interdiction des conteneurs privilégiés ;
- chiffrement obligatoire ;
- quotas ;
- contraintes réseau.

# 18. Security as Code

La sécurité est intégrée au pipeline.

Elle comprend :

- scans ;
- signatures ;
- contrôles ;
- politiques ;
- conformité.

- tests en échec ;
- couverture insuffisante ;
- vulnérabilité critique ;
- qualité insuffisante ;
- dette excessive.

# 22. Gestion des dépendances

- versionnées ;
- surveillées ;
- analysées.

# 23. Analyse statique (SAST)

Analyse du code sans exécution.

Détecte notamment :

- injections ;
- débordements ;
- mauvaises pratiques ;
- erreurs cryptographiques.

---

# 24. Analyse dynamique (DAST)

Analyse de l'application en fonctionnement.

Elle identifie notamment :

- injections ;
- erreurs HTTP ;
- exposition d'informations ;
- authentification faible.

---

# 25. Analyse des composants (SCA)

Le SCA identifie :

- bibliothèques ;
- licences ;
- CVE ;
- versions obsolètes.

---

# 26. Scan des conteneurs

Les images doivent être contrôlées avant publication.

Critères :

- vulnérabilités ;
- packages inutiles ;
- utilisateur root ;
- signatures.

---

# 27. Gestion des secrets

Les secrets sont stockés dans un coffre sécurisé.

Ils ne doivent jamais apparaître :

- dans Git ;
- dans les images ;
- dans les journaux.

La rotation est automatisée.

---

# 28. Signature et provenance des artefacts

Les artefacts doivent être :

- signés ;
- vérifiables ;
- traçables.

La provenance doit permettre de connaître :

- le commit ;
- le pipeline ;
- l'auteur ;
- la date.

---

# 29. Gestion des vulnérabilités

Les vulnérabilités sont :

- détectées ;
- classifiées ;
- priorisées ;
- corrigées ;
- suivies.

Les délais de correction dépendent de leur criticité.

---

# 30. Observabilité du pipeline

Le pipeline lui-même doit être supervisé.

Mesures :

- durée ;
- succès ;
- échecs ;
- étapes lentes ;
- blocages.

---

# 31. GitOps

Git devient la référence officielle.

Le cluster est synchronisé automatiquement avec Git.

Les modifications manuelles sont interdites ou détectées.

# 45. Conclusion

Le **DevSecOps** constitue le moteur industriel de développement des plateformes EduWeb.

Il unifie :

- le développement ;
- la cybersécurité ;
- l'exploitation ;
- la qualité ;
- l'automatisation ;
- la conformité.

Grâce à l'intégration continue, à la livraison continue, aux contrôles de sécurité automatisés, au GitOps, aux infrastructures décrites comme du code, aux politiques codifiées et à une observabilité native, EduWeb peut produire des logiciels de manière rapide, fiable et sécurisée tout en maintenant un haut niveau de gouvernance.

Le document suivant, **OPS-017 — AIOps**, décrira comment l'intelligence artificielle peut renforcer l'exploitation en détectant automatiquement les anomalies, en corrélant les événements, en prédisant les incidents, en proposant des actions correctives et en automatisant certaines opérations tout en conservant un contrôle humain sur les décisions critiques.
