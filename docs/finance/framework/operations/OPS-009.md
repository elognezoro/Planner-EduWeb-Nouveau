# 1. Introduction

La continuité d’activité désigne la capacité d’une organisation à maintenir ses fonctions essentielles lorsqu’un événement majeur perturbe son fonctionnement normal.

Ces événements peuvent être :

- une panne d’infrastructure ;
- une coupure d’électricité ;
- une perte de connectivité ;
- une cyberattaque ;
- une corruption de données ;
- une indisponibilité d’un fournisseur ;
- une catastrophe naturelle ;
- une crise sanitaire ;
- une erreur humaine majeure ;
- une défaillance organisationnelle.

La continuité d’activité ne concerne donc pas uniquement les technologies.

Elle couvre également :

- les personnes ;
- les processus ;
- les locaux ;
- les fournisseurs ;
- la communication ;
- la gouvernance ;
- les ressources critiques.

Le **Business Continuity Plan — BCP** vise à préserver les services essentiels et à limiter les conséquences d’une interruption.

---

# 2. Vision

EduWeb met en œuvre une continuité d’activité :

- intégrée à l’architecture d’entreprise ;
- fondée sur les risques ;
- orientée vers les services critiques ;
- testée régulièrement ;
- automatisée lorsque cela est possible ;
- coordonnée avec le plan de reprise d’activité ;
- adaptée aux contextes institutionnels et éducatifs ;
- compatible avec des opérations nationales.

L’objectif est de garantir que les plateformes EduWeb puissent continuer à fournir les services prioritaires, même en mode dégradé, pendant une crise.

---

# 3. Objectifs

Le cadre poursuit les objectifs suivants :

- identifier les activités critiques ;
- évaluer les impacts d’une interruption ;
- définir les priorités de continuité ;
- réduire la durée des interruptions ;
- protéger les données essentielles ;
- maintenir les opérations prioritaires ;
- coordonner les équipes ;
- assurer la communication ;
- maîtriser les dépendances ;
- préparer la reprise normale ;
- satisfaire les engagements contractuels et institutionnels ;
- renforcer la résilience globale.

---

# 6. Concepts fondamentaux

## 6.1 Continuité d’activité

Capacité à poursuivre les activités prioritaires pendant une perturbation.

---

## 6.2 Plan de continuité d’activité

Ensemble documenté de :

- stratégies ;
- procédures ;
- rôles ;
- ressources ;
- scénarios ;
- moyens de communication.

---

## 6.3 Activité critique

Activité dont l’interruption entraîne des conséquences inacceptables.

Exemples :

- authentification ;
- accès aux cours ;
- génération des emplois du temps ;
- validation administrative ;
- réservation de ressources ;
- sauvegarde des données.

---

## 6.4 Service minimum

Niveau réduit mais acceptable de fonctionnement pendant la crise.

---

## 6.5 Mode dégradé

Fonctionnement temporaire avec des capacités limitées.

Exemple :

```text
Consultation autorisée

Création temporairement suspendue
```

---

## 6.6 Maximum Tolerable Period of Disruption

Durée maximale pendant laquelle une activité peut rester interrompue sans provoquer un impact inacceptable.

---

## 6.7 Recovery Time Objective

Durée cible de restauration d’un service.

```text
RTO = Temps maximal visé avant reprise
```

---

## 6.8 Recovery Point Objective

Quantité maximale de données qu’une organisation accepte de perdre, exprimée dans le temps.

```text
RPO = Point de restauration maximal acceptable
```

---

## 6.9 Minimum Business Continuity Objective

Niveau minimal de service devant être maintenu pendant une crise.

---

## 6.10 Plan de reprise d’activité

Dispositif technique permettant de restaurer les systèmes après un sinistre.

Il est traité spécifiquement dans **OPS-010**.

# 8. Analyse d’impact sur les activités

La **Business Impact Analysis — BIA** identifie les conséquences d’une interruption.

---

## 8.1 Dimensions étudiées

| Dimension | Exemples d’impact |
|---|---|
| Opérationnelle | Activité interrompue |
| Financière | Perte de revenus ou coûts supplémentaires |
| Institutionnelle | Blocage d’un service public |
| Réputationnelle | Perte de confiance |
| Juridique | Non-respect d’une obligation |
| Pédagogique | Interruption des apprentissages |
| Sécurité | Exposition de données |
| Sociale | Perturbation des usagers |

---

## 8.2 Questions principales

- Quelle activité est interrompue ?
- Combien d’utilisateurs sont affectés ?
- Combien de temps l’interruption est-elle acceptable ?
- Existe-t-il une procédure manuelle ?
- Quelles données sont indispensables ?
- Quelles ressources humaines sont nécessaires ?
- Quelles dépendances sont critiques ?
- Quel niveau de service minimum doit être maintenu ?

---

## 8.3 Fiche BIA

| Élément | Description |
|---|---|
| Activité | Nom du processus |
| Responsable | Propriétaire métier |
| Criticité | Faible à critique |
| MTPD | Durée maximale tolérable |
| RTO | Délai cible de reprise |
| RPO | Perte de données acceptable |
| MBCO | Niveau minimum attendu |
| Dépendances | Services, données, fournisseurs |
| Solution de continuité | Stratégie prévue |

---

## 8.4 Exemple de classification

| Activité | Criticité | RTO | RPO | Mode dégradé |
|---|:---:|---:|---:|---|
| Authentification | Critique | 15 min | 5 min | Accès limité |
| Consultation des emplois du temps | Critique | 30 min | 15 min | Cache local |
| Génération d’emplois du temps | Élevée | 4 h | 1 h | Traitement différé |
| Réservation de ressources | Élevée | 2 h | 15 min | Registre manuel |
| Reporting stratégique | Moyenne | 24 h | 12 h | Export précédent |
| Archivage historique | Faible | 72 h | 24 h | Suspension temporaire |

# 9. Analyse des risques

La continuité d’activité repose sur une analyse structurée des scénarios de crise.

---

## 9.1 Catégories de risques

### Risques techniques

- panne serveur ;
- saturation ;
- défaut logiciel ;
- panne de stockage ;
- perte réseau.

---

### Risques cyber

- rançongiciel ;
- déni de service ;
- compromission d’un compte ;
- corruption de données ;
- fuite d’informations.

---

### Risques humains

- erreur ;
- indisponibilité d’une équipe ;
- départ d’un expert ;
- fraude ;
- mauvaise procédure.

---

### Risques physiques

- incendie ;
- inondation ;
- catastrophe naturelle ;
- coupure électrique ;
- perte d’accès au site.

---

### Risques fournisseurs

- panne Cloud ;
- interruption d’un opérateur ;
- faillite ;
- rupture de contrat ;
- dépendance technologique.

---

### Risques institutionnels

- changement réglementaire ;
- décision administrative ;
- crise nationale ;
- restriction d’accès ;
- indisponibilité de partenaires publics.

---

## 9.2 Matrice de risque

```text
Risque = Probabilité × Impact
```

| Niveau | Traitement |
|---|---|
| Faible | Acceptation surveillée |
| Modéré | Mesures de réduction |
| Élevé | Plan de continuité obligatoire |
| Critique | Stratégie renforcée et tests fréquents |

---

## 9.3 Scénarios prioritaires

Les scénarios doivent au minimum couvrir :

- indisponibilité totale d’une plateforme ;
- perte d’un centre d’hébergement ;
- corruption de base de données ;
- indisponibilité de l’équipe principale ;
- attaque par rançongiciel ;
- interruption de connectivité nationale ;
- panne d’un fournisseur critique ;
- forte montée en charge ;
- indisponibilité d’un service d’authentification ;
- défaillance DNS.

# 10. Classification des services critiques

## Niveau 1 — Vital

Interruption immédiatement inacceptable.

Exemples :

- authentification ;
- accès aux services nationaux ;
- sécurité ;
- DNS principal ;
- base centrale critique.

---

## Niveau 2 — Critique

Interruption acceptable uniquement pendant une courte durée.

Exemples :

- emplois du temps ;
- réservations ;
- validation administrative ;
- accès aux cours.

---

## Niveau 3 — Important

Interruption temporaire tolérable avec procédure de contournement.

Exemples :

- reporting ;
- export ;
- statistiques ;
- notifications non urgentes.

---

## Niveau 4 — Standard

Service pouvant être suspendu pendant une période plus longue.

Exemples :

- archives secondaires ;
- fonctions expérimentales ;
- documentation non essentielle.

---

# 11. Stratégies de continuité

## 11.1 Redondance

Les composants critiques doivent disposer de mécanismes de redondance.

Exemples :

- plusieurs instances ;
- plusieurs zones ;
- plusieurs fournisseurs ;
- plusieurs liens réseau ;
- plusieurs copies de données.

---

## 11.2 Haute disponibilité

Les services essentiels doivent éviter tout point unique de défaillance.

```text
Load Balancer

↓

Instance A

+

Instance B

+

Instance C
```

---

## 11.3 Résilience géographique

Les ressources doivent être réparties entre plusieurs zones ou sites.

---

## 11.4 Mode dégradé

Certaines fonctions peuvent être temporairement désactivées afin de préserver les fonctions essentielles.

Exemple :

```text
Fonctions critiques maintenues

Fonctions secondaires suspendues
```

---

## 11.5 Mise en file d’attente

Les opérations non urgentes peuvent être stockées temporairement puis rejouées.

Exemple :

- notifications ;
- exports ;
- synchronisations ;
- traitements analytiques.

---

## 11.6 Cache de continuité

Les données de consultation essentielles peuvent être maintenues localement ou dans un cache distribué.

---

## 11.7 Procédures manuelles

Certaines activités doivent disposer d’un mode alternatif.

Exemples :

- registre de réservation ;
- export PDF ;
- tableau local ;
- formulaire papier ;
- validation différée.

---

## 11.8 Travail à distance

Les équipes critiques doivent pouvoir intervenir depuis un autre site avec :

- accès sécurisé ;
- authentification forte ;
- outils de collaboration ;
- procédures documentées.

---

## 11.9 Diversification des fournisseurs

Les dépendances critiques doivent être réduites par :

- plusieurs opérateurs ;
- plusieurs régions Cloud ;
- plusieurs canaux de communication ;
- procédures de substitution.

---

## 11.10 Réduction de fonctionnalité

Le système peut appliquer une stratégie de **graceful degradation**.

Exemple :

```text
Désactiver l’analytique avancée

↓

Maintenir l’accès aux fonctions essentielles
```

## 13.2 Structure de commandement

```text

├── Coordination technique
├── Coordination métier
├── Sécurité
├── Communication
├── Logistique
└── Relations institutionnelles
```

---

## 13.3 Rôles

| Rôle | Responsabilité |
|---|---|
| Directeur de crise | Décisions stratégiques |
| Business Continuity Manager | Coordination du PCA |
| Incident Commander | Pilotage opérationnel |
| Technical Lead | Restauration technique |
| Business Lead | Priorisation des activités |
| Security Lead | Gestion des risques cyber |
| Communication Lead | Messages internes et externes |

## 13.4 Activation

La cellule est activée lorsque :

- un service vital est interrompu ;
- le RTO risque d’être dépassé ;
- plusieurs établissements sont affectés ;
- une crise de sécurité est confirmée ;
- une décision institutionnelle majeure est requise ;
- un fournisseur critique devient indisponible.

---

| Niveau | Description |
|---|---|
| C1 | Incident local maîtrisé |
| C2 | Impact sur plusieurs services |
| C3 | Crise institutionnelle majeure |
| C4 | Crise nationale ou multisite |

- la synchronisation ultérieure ;

- contrôle les doublons après rétablissement.

- priorité aux examens ;

- communication aux apprenants.

# 28. Conclusion

La **Continuité d’Activité** constitue une capacité stratégique de l’architecture opérationnelle d’EduWeb. Elle permet de préserver les activités essentielles, de maintenir un niveau de service minimal et de coordonner efficacement les équipes lorsqu’une perturbation majeure affecte les systèmes, les fournisseurs, les locaux ou les ressources humaines.

Le cadre proposé combine l’analyse d’impact métier, l’évaluation des risques, la classification des services critiques, les modes dégradés, la redondance, la résilience géographique, les procédures alternatives, la gestion de crise et la communication institutionnelle. Les tests réguliers garantissent que les plans restent réellement exploitables.

Cette architecture prépare directement le **Plan de Reprise d’Activité**, décrit dans **OPS-010**, qui définira les mécanismes techniques et organisationnels de restauration des infrastructures, des applications et des données après un sinistre majeur.
