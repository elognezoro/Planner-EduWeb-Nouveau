# 1. Introduction

Les architectures microservices permettent de décomposer une application complexe en services autonomes, spécialisés et déployables indépendamment.

Cette approche peut apporter :

- une meilleure modularité ;
- une évolution plus rapide ;
- une autonomie accrue des équipes ;
- une scalabilité ciblée ;
- une meilleure isolation des responsabilités ;
- une capacité de déploiement différenciée.

Elle introduit cependant de nouvelles contraintes opérationnelles.

Une application monolithique est généralement exploitée comme un ensemble unique.

Une architecture microservices repose sur :

- plusieurs services ;
- plusieurs versions ;
- plusieurs bases de données ;
- plusieurs flux ;
- plusieurs dépendances ;
- plusieurs points de défaillance ;
- plusieurs équipes ;
- plusieurs pipelines.

La complexité n’est donc pas supprimée. Elle est distribuée.

```text
Complexité applicative centralisée

↓

Complexité opérationnelle distribuée
```

L’exploitation des microservices doit permettre à EduWeb de conserver les bénéfices de cette architecture sans perdre :

- la visibilité ;
- la sécurité ;
- la cohérence ;
- la maîtrise des coûts ;
- la capacité de diagnostic ;
- la gouvernance ;
- la qualité de service.

# 6. Concepts fondamentaux

## 6.1 Microservice

Service logiciel autonome réalisant une capacité métier ou technique clairement délimitée.

Exemples :

- authentification ;
- gestion des établissements ;
- génération d’emplois du temps ;
- notification ;
- réservation ;
- paiement ;
- gestion documentaire.

---

## 6.2 Domaine métier

Ensemble cohérent de responsabilités fonctionnelles.

Exemple :

```text
Domaine :
Gestion des emplois du temps

Microservices :
- Paramétrage
- Contraintes
- Génération
- Validation
- Publication
```

---

## 6.3 Bounded Context

Périmètre dans lequel un modèle métier possède une signification cohérente.

---

## 6.4 Service autonome

Service pouvant :

- être développé ;
- être testé ;
- être déployé ;
- être surveillé ;
- évoluer ;

sans imposer systématiquement une modification simultanée des autres services.

---

## 6.5 Contrat de service

Définition formelle des échanges d’un service.

Il peut inclure :

- API ;
- événements ;
- schémas ;
- erreurs ;
- sécurité ;
- version ;
- engagements de performance.

---

## 6.6 Sidecar

Composant auxiliaire exécuté à proximité d’un service.

Exemples :

- proxy réseau ;
- agent de télémétrie ;
- agent de sécurité ;
- gestionnaire de secrets.

---

## 6.7 Service Mesh

Couche d’infrastructure gérant les communications entre microservices.

---

## 6.8 API Gateway

Point d’entrée contrôlé pour les appels provenant des utilisateurs ou des systèmes externes.

---

## 6.9 Circuit Breaker

Mécanisme interrompant temporairement les appels vers une dépendance défaillante.

---

## 6.10 Bulkhead

Mécanisme d’isolation empêchant la saturation d’un composant de bloquer l’ensemble du système.

---

## 6.11 Retry

Nouvelle tentative après un échec temporaire.

---

## 6.12 Timeout

Durée maximale d’attente d’une réponse.

---

## 6.13 Eventual Consistency

Modèle dans lequel les données deviennent cohérentes après un délai.

---

## 6.14 Saga

Mécanisme coordonnant plusieurs transactions locales dans un processus distribué.

---

## 6.15 Dead Letter Queue

File recevant les messages qui n’ont pas pu être traités correctement.

# 8. Caractéristiques opérationnelles des microservices

## 8.1 Distribution

Les composants sont répartis sur plusieurs nœuds et réseaux.

---

## 8.2 Dépendances

Un service peut dépendre :

- d’un autre service ;
- d’une base ;
- d’un cache ;
- d’une file ;
- d’une API externe ;
- d’un fournisseur.

---

## 8.3 Latence

Chaque appel réseau ajoute un délai.

```text
Temps total

=

Temps du service A

+

Temps réseau

+

Temps du service B

+

Temps base

+

Temps des autres dépendances
```

---

## 8.4 Défaillances partielles

Une partie du système peut être indisponible tandis que les autres composants continuent de fonctionner.

---

## 8.5 Versions multiples

Plusieurs versions d’un même service peuvent fonctionner simultanément pendant :

- un déploiement canary ;
- une migration ;
- une période de compatibilité ;
- un test A/B.

---

## 8.6 Données distribuées

Chaque microservice peut posséder ses propres données.

Cela implique :

- réplication ;
- événements ;
- cohérence différée ;
- gestion des doublons ;
- résolution de conflits.

---

## 8.7 Éphémérité

Les conteneurs peuvent être créés, déplacés ou supprimés rapidement.

Les données persistantes ne doivent pas dépendre du cycle de vie d’une instance.

# 16. Communication interservices

## 16.1 Communication synchrone

Exemples :

- REST ;
- gRPC ;
- GraphQL interne.

Avantages :

- réponse immédiate ;
- simplicité de certains parcours.

Risques :

- couplage temporel ;
- latence ;
- propagation des pannes ;
- chaînes d’appels.

---

## 16.2 Communication asynchrone

Exemples :

- événements ;
- files ;
- topics ;
- messages.

Avantages :

- découplage ;
- absorption des pics ;
- résilience ;
- reprise.

Risques :

- cohérence différée ;
- doublons ;
- ordre ;
- diagnostic plus complexe.

---

## 16.3 Choix

Le mode de communication doit dépendre :

- du besoin de réponse immédiate ;
- du niveau de cohérence ;
- de la criticité ;
- du volume ;
- de la tolérance à la latence ;
- de la résilience attendue.

---

## 16.4 Anti-pattern

Une longue chaîne synchrone doit être évitée.

```text
Service A

↓

Service B

↓

Service C

↓

Service D

↓

Service E
```

Une défaillance de E peut bloquer tout le parcours.

# 20. Supervision et health checks

## 20.1 Liveness Probe

Vérifie si l’instance fonctionne.

Une erreur peut déclencher un redémarrage.

---

## 20.2 Readiness Probe

Vérifie si l’instance peut recevoir du trafic.

---

## 20.3 Startup Probe

Vérifie le démarrage des services nécessitant un temps d’initialisation important.

---

## 20.4 Health Check métier

Un service peut être techniquement vivant mais fonctionnellement inutilisable.

Exemple :

```text
Le service répond HTTP 200

mais

ne peut plus enregistrer une réservation
```

Les parcours critiques doivent donc être contrôlés.

---

## 20.5 Dépendances

Un health check ne doit pas systématiquement déclarer un service indisponible parce qu’une dépendance secondaire est défaillante.

# 51. Conclusion

L’**Exploitation des Microservices** constitue un pilier essentiel de l’architecture opérationnelle d’EduWeb. Elle permet de tirer parti de la modularité, de l’autonomie, de la scalabilité et de la rapidité d’évolution des architectures distribuées tout en maîtrisant leur complexité.

Cette discipline associe :

```text
Autonomie des services

+

Contrats explicites

+

Automatisation

+

Observabilité

+

Résilience

+

Sécurité

+

Gouvernance
```

Grâce à la conteneurisation, à l’orchestration, à l’API Gateway, au service mesh, aux communications événementielles, aux stratégies de résilience, aux déploiements progressifs et à l’observabilité distribuée, les plateformes EduWeb peuvent évoluer de manière indépendante sans compromettre leur stabilité globale.

Chaque microservice doit néanmoins rester justifié par un besoin réel. Une architecture distribuée excessive peut augmenter les coûts, les dépendances et la charge opérationnelle. Le choix entre monolithe modulaire et microservices doit donc être fondé sur la complexité métier, les besoins de scalabilité, l’autonomie des équipes et les exigences de déploiement.

Le document suivant, **OPS-016 — DevSecOps**, définira l’intégration continue de la sécurité, de la qualité, de l’automatisation et des opérations dans l’ensemble du cycle de développement et de déploiement des plateformes EduWeb.
