# 1. Introduction

Les environnements numériques modernes produisent un volume très important de données opérationnelles :

- métriques ;
- journaux ;
- traces ;
- événements ;
- alertes ;
- tickets ;
- changements ;
- configurations ;
- données de capacité ;
- données de sécurité ;
- informations métier.

Dans une architecture distribuée composée de microservices, de bases de données, de conteneurs, d’API, de services Cloud et de fournisseurs externes, la capacité humaine seule ne suffit plus toujours à :

- analyser tous les signaux ;
- distinguer les alertes importantes ;
- identifier rapidement les causes ;
- anticiper les incidents ;
- recommander les actions adaptées ;
- maintenir une vision globale du système.

L’AIOps, ou **Artificial Intelligence for IT Operations**, applique l’intelligence artificielle et l’apprentissage automatique aux opérations informatiques.

L’objectif n’est pas de remplacer les équipes d’exploitation, mais de les aider à :

- comprendre plus rapidement ;
- décider avec davantage d’informations ;
- automatiser les tâches répétitives ;
- réduire les délais de résolution ;
- prévenir les pannes ;
- améliorer la fiabilité.

```text
Données opérationnelles

+

Intelligence artificielle

+

Automatisation

+

Expertise humaine

=

AIOps
```


# 6. Concepts fondamentaux

## 6.1 AIOps

Utilisation de techniques d’intelligence artificielle pour analyser et automatiser les opérations informatiques.

---

## 6.2 Anomalie

Comportement différent du comportement attendu.

Exemples :

- hausse inhabituelle de latence ;
- croissance anormale des erreurs ;
- consommation mémoire inhabituelle ;
- baisse du taux de transactions réussies ;
- changement soudain du volume d’utilisateurs.

---

## 6.3 Baseline

Référence décrivant le comportement normal d’un système.

Une baseline peut dépendre :

- de l’heure ;
- du jour ;
- de la saison ;
- de la période scolaire ;
- de la région ;
- du type d’utilisateur.

---

## 6.4 Corrélation

Regroupement de signaux liés à une même situation.

---

## 6.5 Causalité

Relation selon laquelle un événement ou un changement produit un effet.

La corrélation ne prouve pas toujours la causalité.

---

## 6.6 Root Cause Analysis

Analyse visant à identifier la cause principale d’un incident.

---

## 6.7 Prediction

Estimation d’un événement futur à partir de données historiques et actuelles.

---

## 6.8 Recommendation

Proposition d’action fondée sur l’analyse du contexte.

---

## 6.9 Automated Remediation

Exécution automatique d’une action corrective.

---

## 6.10 Closed-Loop Automation

Boucle complète :

```text
Détection

↓

Analyse

↓

Décision

↓

Action

↓

Validation

↓

Apprentissage
```

---

## 6.11 Confidence Score

Niveau de confiance associé à une prédiction ou à une recommandation.

---

## 6.12 Feedback Loop

Mécanisme permettant aux opérateurs de confirmer ou de corriger une recommandation afin d’améliorer le modèle.

# 8. Niveaux de maturité AIOps

## Niveau 0 — Manuel

Les équipes analysent manuellement les alertes et les incidents.

```text
Alertes

↓

Analyse humaine

↓

Action manuelle
```

---

## Niveau 1 — Centralisé

Les données sont regroupées dans une plateforme commune.

---

## Niveau 2 — Assisté

L’IA :

- détecte les anomalies ;
- réduit le bruit ;
- recommande des causes ;
- enrichit les tickets.

---

## Niveau 3 — Proactif

L’IA prédit les risques et propose des actions préventives.

---

## Niveau 4 — Automatisé

Les remédiations à faible risque sont exécutées automatiquement.

---

## Niveau 5 — Autonome sous contrôle

Le système réalise une boucle fermée, avec :

- politiques ;
- limites ;
- contrôle humain ;
- audit ;
- mécanisme d’arrêt.

# 12. Ingestion et normalisation

## 12.1 Ingestion temps réel

Les événements critiques doivent être ingérés avec une faible latence.

---

## 12.2 Ingestion par lots

Les historiques et les référentiels peuvent être intégrés périodiquement.

---

## 12.3 Normalisation

Les données hétérogènes doivent être harmonisées.

Exemple :

```text
host

server

node

instance
```

peuvent être normalisés vers :

```text
resource_id
```

---

## 12.4 Enrichissement

Les données peuvent être enrichies avec :

- le propriétaire ;
- la criticité ;
- la région ;
- le service métier ;
- la version ;
- le changement récent ;
- le SLO.

---

## 12.5 Déduplication

Les événements identiques ou très proches doivent être regroupés.

---

## 12.6 Gestion du temps

Les horodatages doivent être :

- synchronisés ;
- normalisés ;
- associés à un fuseau ;
- suffisamment précis.

# 15. Détection d’anomalies

## 15.1 Seuil statique

Exemple :

```text
CPU > 90 %
```

Simple, mais parfois insuffisant.

---

## 15.2 Seuil dynamique

Le seuil dépend du comportement normal.

Exemple :

```text
CPU à 75 %
peut être normal à 10 h

mais anormal à 02 h
```

---

## 15.3 Détection univariée

Analyse d’une métrique individuelle.

---

## 15.4 Détection multivariée

Analyse plusieurs variables ensemble.

Exemple :

```text
Latence

+

Taux d’erreur

+

Longueur de file

+

CPU
```

---

## 15.5 Anomalie contextuelle

Une valeur est anormale uniquement dans un contexte particulier.

---

## 15.6 Anomalie collective

Une série de petits écarts peut constituer une anomalie significative.

---

## 15.7 Saison

Les modèles doivent prendre en compte :

- heures ;
- jours ;
- périodes scolaires ;
- rentrée ;
- examens ;
- campagnes nationales.

---

## 16.6 Corrélation métier

# 17. Réduction du bruit

## 17.1 Problème

Une plateforme peut produire des milliers d’alertes.

Une grande partie peut être :

- redondante ;
- secondaire ;
- non actionnable ;
- liée à la même cause.

---

## 17.2 Déduplication

Les alertes identiques sont regroupées.

---

## 17.3 Suppression

Les alertes liées à une maintenance connue peuvent être supprimées temporairement.

---

## 17.4 Agrégation

Plusieurs alertes deviennent un seul incident.

---

## 17.5 Priorisation

Les alertes sont classées selon :

- impact ;
- criticité ;
- utilisateurs ;
- SLO ;
- propagation ;
- probabilité.

---

## 17.6 Objectif

# 54. Conclusion

L’**AIOps** permet à EduWeb de faire évoluer ses opérations vers un modèle plus intelligent, plus prédictif et plus automatisé.

Cette architecture associe :

```text
Observabilité

+

Données opérationnelles

+

Intelligence artificielle

+

Automatisation

+

Contrôle humain
```

Elle permet de détecter plus tôt les anomalies, de réduire le bruit, de corréler les événements, d’identifier les causes probables, de prévoir les incidents et de recommander des actions adaptées.

L’AIOps ne doit toutefois pas être considéré comme une automatisation aveugle. Sa réussite dépend de la qualité des données, de la fiabilité de la topologie, de l’explicabilité des modèles, de la sécurité des actions et de la capacité des opérateurs à conserver le contrôle des décisions critiques.

La progression vers une exploitation autonome doit être graduelle. Elle doit commencer par l’assistance, se poursuivre par la prédiction et n’aboutir à l’automatisation que lorsque les actions sont suffisamment sûres, testées, réversibles et gouvernées.

Le document suivant, **OPS-018 — Site Reliability Engineering**, définira l’organisation, les pratiques, les indicateurs et les mécanismes permettant de piloter la fiabilité des services EduWeb à partir des SLI, des SLO, des budgets d’erreur, de l’automatisation et de l’ingénierie opérationnelle.
