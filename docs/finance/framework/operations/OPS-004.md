# 1. Introduction

Un incident est un événement non planifié qui :

- interrompt un service ;
- dégrade ses performances ;
- compromet sa sécurité ;
- réduit sa qualité ;
- empêche un utilisateur d’accomplir une tâche attendue.

La gestion des incidents vise avant tout à restaurer le service normal dans les meilleurs délais.

Elle ne cherche pas nécessairement, dans un premier temps, à éliminer la cause profonde. Cette responsabilité relève principalement de la gestion des problèmes décrite dans le document **OPS-005**.

---

# 2. Vision

EduWeb met en œuvre une gestion des incidents :

- centralisée ;
- structurée ;
- automatisée ;
- mesurable ;
- collaborative ;
- orientée utilisateur ;
- améliorée par l’intelligence artificielle.

L’objectif est de réduire au maximum :

- le temps de détection ;
- le temps de qualification ;
- le temps de résolution ;
- l’impact sur les utilisateurs.

---

# 3. Objectifs

Le processus poursuit les objectifs suivants :

- restaurer rapidement les services ;
- limiter les impacts opérationnels ;
- garantir une prise en charge cohérente ;
- améliorer la communication ;
- assurer une traçabilité complète ;
- capitaliser les enseignements ;
- prévenir la répétition des incidents.

---

# 4. Principes directeurs

La gestion des incidents repose sur les principes suivants :

- Incident Management by Design
- Restore Service First
- User Impact First
- Single Point of Coordination
- Automation First
- Clear Ownership
- Full Traceability
- Continuous Improvement
- Blameless Culture
- Human Supervision

L’objectif prioritaire est le rétablissement du service.

# 6. Définition et classification des incidents

## 6.1 Incident technique

Exemples :

- serveur indisponible ;
- base de données inaccessible ;
- API en erreur ;
- saturation du stockage.

---

## 6.2 Incident applicatif

Exemples :

- écran inaccessible ;
- fonctionnalité défaillante ;
- erreurs récurrentes ;
- calcul incorrect.

---

## 6.3 Incident de sécurité

Exemples :

- tentative d’intrusion ;
- compte compromis ;
- accès non autorisé ;
- fuite potentielle de données.

---

## 6.4 Incident métier

Exemples :

- inscription impossible ;
- réservation bloquée ;
- emploi du temps non généré ;
- validation administrative interrompue.

---

## 6.5 Incident utilisateur

Exemples :

- mot de passe oublié ;
- accès refusé ;
- dysfonctionnement local ;
- mauvaise configuration.

---

## 6.6 Incident fournisseur

Exemples :

- indisponibilité d’un service Cloud ;
- panne d’un fournisseur de paiement ;
- rupture d’une API partenaire ;
- coupure de connectivité.

# 7. Cycle de vie d’un incident

```text
Détection

↓

Enregistrement

↓

Qualification

↓

Catégorisation

↓

Priorisation

↓

Affectation

↓

Diagnostic

↓

Résolution

↓

Validation

↓

Clôture

↓

Capitalisation
```

Chaque étape est horodatée et auditée.

---

## 7.1 Détection

L’incident peut être détecté par :

- une alerte automatique ;
- un utilisateur ;
- un administrateur ;
- un outil de sécurité ;
- un partenaire.

---

## 7.2 Enregistrement

Un ticket d’incident est créé avec :

- identifiant unique ;
- date et heure ;
- source ;
- service concerné ;
- description ;
- impact ;
- urgence ;
- pièces jointes ;
- responsable initial.

---

## 7.3 Qualification

L’équipe vérifie :

- la réalité de l’incident ;
- son périmètre ;
- son impact ;
- sa reproductibilité ;
- son niveau de criticité.

---

## 7.4 Diagnostic

Le diagnostic exploite :

- métriques ;
- journaux ;
- traces ;
- événements ;
- historique ;
- base de connaissances.

---

## 7.5 Résolution

La résolution peut consister à :

- redémarrer un service ;
- appliquer un correctif ;
- basculer vers une infrastructure de secours ;
- restaurer une sauvegarde ;
- désactiver temporairement une fonctionnalité ;
- appliquer une solution de contournement.

---

## 7.6 Validation

Le rétablissement est confirmé par :

- les outils de monitoring ;
- l’équipe opérationnelle ;
- les utilisateurs concernés ;
- le responsable métier.

---

## 7.7 Clôture

La clôture nécessite :

- une cause apparente documentée ;
- une solution décrite ;
- une validation ;
- une classification finale ;
- un éventuel transfert vers la gestion des problèmes.

# 9. Priorisation et niveaux de sévérité

La priorité résulte de la combinaison de l’impact et de l’urgence.

| Niveau | Description | Exemple | Délai de prise en charge |
|---|---|---|---:|
| P1 — Critique | Service national indisponible | Affectation nationale bloquée | Immédiat |
| P2 — Majeur | Service fortement dégradé | Paiements ou réservations perturbés | < 15 min |
| P3 — Modéré | Impact limité | Fonction secondaire indisponible | < 1 h |
| P4 — Faible | Gêne mineure | Problème isolé d’affichage | < 8 h |
| P5 — Information | Demande sans interruption | Question utilisateur | Planifiée |

---

## Matrice d’impact

| Impact | Définition |
|---|---|
| Critique | Institution ou service national affecté |
| Élevé | Plusieurs établissements affectés |
| Moyen | Un établissement ou un groupe d’utilisateurs |
| Faible | Un utilisateur ou une fonctionnalité non critique |

---

## Matrice d’urgence

| Urgence | Définition |
|---|---|
| Immédiate | Aucun contournement possible |
| Élevée | Contournement limité |
| Moyenne | Contournement disponible |
| Faible | Impact acceptable à court terme |

# 10. Gestion des incidents majeurs

Un incident majeur est un incident dont l’impact nécessite :

- une mobilisation immédiate ;
- une coordination renforcée ;
- une communication institutionnelle ;
- un pilotage dédié.

---

## 10.1 Critères

Un incident est majeur lorsqu’il affecte notamment :

- une plateforme nationale ;
- un grand nombre d’utilisateurs ;
- un processus critique ;
- des données sensibles ;
- la sécurité globale ;
- la réputation institutionnelle.

---

## 10.2 Cellule de crise

La cellule de crise peut comprendre :

- Incident Manager ;
- Responsable des opérations ;
- Responsable sécurité ;
- Responsable applicatif ;
- Responsable infrastructure ;
- Responsable métier ;
- Responsable communication ;
- Direction générale.

---

## 10.3 Commandement

```text
Incident Commander

↓

Technical Lead

↓

Business Lead

↓

Communication Lead

↓

Resolution Teams
```

Un responsable unique coordonne les actions.

---

## 10.4 Chronologie d’un incident majeur

↓

# 11. Communication et escalade

## 11.1 Communication interne

Les équipes reçoivent :

- statut ;
- impact ;
- actions en cours ;
- responsable ;
- prochaine mise à jour.

---

## 11.2 Communication utilisateur

Les utilisateurs doivent être informés avec un message :

- clair ;
- factuel ;
- non technique ;
- transparent ;
- régulièrement actualisé.

---

## 11.3 Canaux

Les communications peuvent utiliser :

- tableau de bord de statut ;
- e-mail ;
- SMS ;
- notifications mobiles ;
- messagerie collaborative ;
- portail institutionnel.

---

## 11.4 Escalade fonctionnelle

L’incident est transféré à une équipe plus spécialisée lorsque le niveau courant ne peut pas le résoudre.

---

## 11.5 Escalade hiérarchique

La direction est informée lorsque :

- les SLA risquent d’être dépassés ;
- l’impact augmente ;
- une décision stratégique est nécessaire ;
- la réputation institutionnelle est en jeu.

---

# 12. Gouvernance

Chaque incident comporte au minimum :

- un identifiant ;
- une source ;
- une catégorie ;
- une priorité ;
- un service concerné ;
- un responsable ;
- un historique ;
- une résolution ;
- une validation ;
- une date de clôture.

---

## Rôles principaux

| Rôle | Responsabilité |
|---|---|
| Service Desk | Réception et traitement initial |
| Incident Manager | Coordination globale |
| Support N1 | Diagnostic de premier niveau |
| Support N2 | Expertise applicative ou infrastructure |
| Support N3 | Expertise avancée et ingénierie |
| Responsable métier | Validation de l’impact et du rétablissement |
| Security Operations | Traitement des incidents de sécurité |
| Problem Manager | Analyse des causes récurrentes |

---

## Principes de gouvernance

- séparation des responsabilités ;
- traçabilité complète ;
- validation des clôtures ;
- revue périodique ;
- contrôle des SLA ;
- protection des données sensibles.

# 14. Automatisation et AIOps

L’automatisation peut intervenir à plusieurs niveaux.

---

## Création automatique de tickets

Une alerte critique génère automatiquement un incident.

---

## Classification automatique

L’IA détermine :

- la catégorie ;
- la gravité ;
- le groupe responsable.

---

## Corrélation d’incidents

Plusieurs alertes peuvent être regroupées en un seul incident.

---

## Suggestion de résolution

Le système recherche automatiquement :

- des incidents similaires ;
- des procédures ;
- des correctifs ;
- des solutions de contournement.

---

## Remédiation automatisée

Pour les incidents à faible risque, le système peut :

- redémarrer un service ;
- augmenter les ressources ;
- basculer vers un nœud de secours ;
- vider un cache ;
- renouveler un certificat.

---

## Limites de l’automatisation

Une validation humaine reste obligatoire pour :

- les incidents de sécurité sensibles ;
- les restaurations de données majeures ;
- les changements irréversibles ;
- les situations à fort impact métier ;
- les interventions réglementées.

# 15. Cas d’usage EduWeb

## Exemple 1 — EduWeb Planner

Le moteur de génération d’emplois du temps devient indisponible.

Le système :

- détecte l’erreur ;
- crée un incident P1 ;
- affecte l’équipe applicative ;
- active un service de secours ;
- informe les établissements ;
- suit le rétablissement.

---

## Exemple 2 — EduWeb Governance

Les utilisateurs ne peuvent plus valider des décisions administratives.

L’observabilité identifie une erreur d’authentification entre deux microservices.

Le système :

- ouvre un incident P2 ;
- suggère une procédure connue ;
- rétablit le service ;
- clôture après validation métier.

---

## Exemple 3 — EduWeb Booking

Des réservations sont dupliquées.

L’équipe :

- suspend temporairement les confirmations automatiques ;
- applique un mécanisme de déduplication ;
- corrige les dossiers concernés ;
- informe les utilisateurs.

---

## Exemple 4 — E-School EduWeb

Un grand nombre d’apprenants ne peuvent plus accéder aux cours.

L’incident est déclaré majeur.

La cellule de crise :

- augmente la capacité Cloud ;
- isole le composant défaillant ;
- restaure les accès ;
- publie des mises à jour régulières.

---

## Exemple 5 — Ministère

Pendant une campagne nationale, un service central ralentit fortement.

Le système :

- corrèle les alertes ;
- identifie une saturation de base de données ;
- déclenche une montée en capacité ;
- ouvre un incident majeur ;
- maintient le service en mode dégradé ;
- rétablit progressivement la totalité des fonctions.

# 20. Conclusion

La **Gestion des Incidents** constitue un processus essentiel de l’architecture opérationnelle d’EduWeb. Elle permet de rétablir rapidement les services, de limiter les impacts sur les utilisateurs et d’assurer une coordination efficace entre les équipes techniques, métier, sécurité et directionnelles.

Grâce à l’intégration du monitoring, de l’observabilité, de l’automatisation, des workflows d’escalade et de l’intelligence artificielle, le cadre proposé transforme la gestion des incidents en une capacité proactive, mesurable et continuellement améliorée. La capitalisation des retours d’expérience et le transfert des incidents récurrents vers la **Gestion des Problèmes**, décrite dans **OPS-005**, permettent d’éliminer progressivement les causes profondes et d’accroître durablement la fiabilité de l’écosystème EduWeb.
