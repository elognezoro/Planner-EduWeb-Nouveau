# 1. Introduction

Toute évolution d’un système d’information peut générer des bénéfices, mais également introduire :

- des interruptions ;
- des régressions ;
- des vulnérabilités ;
- des incohérences de données ;
- des impacts sur les utilisateurs ;
- des risques réglementaires.

La gestion des changements vise à garantir que chaque modification soit réalisée de manière :

- planifiée ;
- évaluée ;
- autorisée ;
- testée ;
- traçable ;
- réversible lorsque cela est nécessaire.

Elle constitue le lien opérationnel entre :

- la gestion des problèmes ;
- l’ingénierie ;
- les développements ;
- les opérations ;
- la sécurité ;
- les métiers.

---

# 2. Vision

EduWeb met en œuvre une gestion des changements :

- rigoureuse ;
- proportionnée au risque ;
- automatisée lorsque cela est possible ;
- intégrée aux chaînes DevSecOps ;
- fondée sur la traçabilité ;
- orientée vers la continuité de service ;
- gouvernée par des règles claires.

L’objectif n’est pas de ralentir l’innovation, mais de permettre des évolutions rapides tout en maintenant la stabilité et la sécurité de l’écosystème.

---

# 3. Objectifs

Le processus poursuit les objectifs suivants :

- réduire les incidents liés aux changements ;
- maîtriser les impacts ;
- garantir la continuité des services ;
- assurer une validation adéquate ;
- coordonner les équipes ;
- améliorer la traçabilité ;
- renforcer la conformité ;
- soutenir les déploiements fréquents ;
- faciliter le retour arrière ;
- favoriser l’amélioration continue.

---

# 4. Principes directeurs

La gestion des changements repose sur les principes suivants :

- Change by Design
- Risk-Based Approval
- Security by Default
- Automation First
- Small and Reversible Changes
- Full Traceability
- Separation of Duties
- Test Before Production
- Business Impact Awareness
- Continuous Improvement

Chaque changement doit être proportionné à son niveau de risque.

# 6. Définition du changement

Un changement est toute addition, modification ou suppression pouvant affecter directement ou indirectement un service.

Exemples :

- mise à jour d’une application ;
- changement de configuration ;
- évolution d’une base de données ;
- ajout d’un serveur ;
- modification d’une règle métier ;
- migration Cloud ;
- remplacement d’un fournisseur ;
- modification d’un mécanisme de sécurité ;
- déploiement d’un nouveau modèle d’intelligence artificielle ;
- activation d’une nouvelle fonctionnalité.

---

# 7. Typologie des changements

## 7.1 Changement standard

Changement :

- fréquent ;
- documenté ;
- à faible risque ;
- préautorisé ;
- reproductible.

Exemples :

- renouvellement d’un certificat ;
- création d’un compte technique ;
- augmentation contrôlée d’un espace disque ;
- redémarrage planifié d’un service.

---

## 7.2 Changement normal

Changement nécessitant :

- une analyse ;
- une approbation ;
- une planification ;
- des tests ;
- un suivi.

Exemples :

- nouvelle version applicative ;
- modification d’architecture ;
- migration de base de données ;
- activation d’un nouveau module.

---

## 7.3 Changement majeur

Changement présentant :

- un fort impact ;
- un risque élevé ;
- une portée institutionnelle ;
- des conséquences importantes en cas d’échec.

Exemples :

- migration complète vers un nouveau Cloud ;
- remplacement du système d’authentification ;
- déploiement national d’une nouvelle plateforme ;
- modification du modèle de données central.

---

## 7.4 Changement d’urgence

Changement devant être réalisé rapidement pour :

- restaurer un service critique ;
- corriger une vulnérabilité majeure ;
- empêcher une perte de données ;
- répondre à une menace imminente.

---

## 7.5 Changement expérimental

Changement réalisé dans un environnement contrôlé afin d’évaluer :

- une technologie ;
- une architecture ;
- une méthode ;
- un algorithme ;
- une fonctionnalité.

---

## 7.6 Changement réglementaire

Changement imposé par :

- une loi ;
- une norme ;
- une autorité ;
- une politique institutionnelle ;
- une exigence contractuelle.

# 8. Cycle de vie d’un changement

```text
Soumission

↓

Enregistrement

↓

Qualification

↓

Analyse d’impact

↓

Analyse de risque

↓

Classification

↓

Autorisation

↓

Planification

↓

Préparation

↓

Test

↓

Déploiement

↓

Validation

↓

Revue post-implémentation

↓

Clôture

↓

Capitalisation
```

Chaque étape est horodatée et auditée.

---

## 8.1 Soumission

La demande de changement doit préciser :

- le besoin ;
- l’objectif ;
- le périmètre ;
- les composants concernés ;
- les impacts attendus ;
- la date souhaitée ;
- le responsable ;
- les risques connus ;
- le plan de retour arrière.

---

## 8.2 Qualification

La demande est vérifiée afin de déterminer :

- sa complétude ;
- sa catégorie ;
- son niveau de criticité ;
- les équipes concernées ;
- les dépendances ;
- les approbations nécessaires.

---

## 8.3 Analyse

L’analyse évalue :

- l’impact technique ;
- l’impact métier ;
- l’impact sur les données ;
- l’impact sécurité ;
- l’impact financier ;
- l’impact réglementaire ;
- l’impact utilisateur ;
- l’impact sur les SLA.

---

## 8.4 Autorisation

Le changement est :

- approuvé ;
- rejeté ;
- reporté ;
- renvoyé pour complément.

---

## 8.5 Préparation

La préparation comprend :

- documentation ;
- scripts ;
- sauvegardes ;
- tests ;
- plan de communication ;
- plan de retour arrière ;
- ressources humaines ;
- fenêtre de déploiement.

---

## 8.6 Mise en œuvre

Le changement est exécuté selon une procédure approuvée.

Toutes les actions sont journalisées.

---

## 8.7 Validation

Le changement est validé selon :

- les tests techniques ;
- les tests métier ;
- les indicateurs de performance ;
- l’absence de régression ;
- la conformité sécurité ;
- le retour des utilisateurs.

---

## 8.8 Revue post-implémentation

La revue détermine :

- si les objectifs ont été atteints ;
- si des incidents ont été générés ;
- si le risque a été correctement évalué ;
- si la procédure doit être améliorée ;
- si le changement peut devenir standard.

# 10. Évaluation des impacts et des risques

## 10.1 Dimensions d’impact

| Dimension | Questions principales |
|---|---|
| Métier | Quels processus seront affectés ? |
| Utilisateur | Combien d’utilisateurs seront concernés ? |
| Technique | Quels composants seront modifiés ? |
| Données | Une migration ou une transformation est-elle prévue ? |
| Sécurité | Le niveau de protection évolue-t-il ? |
| Réglementaire | Une obligation doit-elle être respectée ? |
| Opérationnel | Une interruption est-elle nécessaire ? |
| Financier | Quels coûts et risques financiers existent ? |

---

## 10.2 Score de risque

Une formule indicative peut être utilisée :

```text
Risque = Probabilité × Impact × Complexité × Criticité
```

Exemple d’échelle :

| Score | Niveau |
|---:|---|
| 1 à 20 | Faible |
| 21 à 50 | Modéré |
| 51 à 80 | Élevé |
| 81 à 100 | Critique |

---

## 10.3 Facteurs aggravants

- changement irréversible ;
- absence de tests ;
- dépendances mal connues ;
- intervention pendant une période critique ;
- absence de sauvegarde ;
- impacts multi-plateformes ;
- fournisseur externe non maîtrisé ;
- forte sensibilité des données.

---

## 10.4 Facteurs réducteurs

- changement automatisé ;
- procédure éprouvée ;
- environnement de préproduction fidèle ;
- rollback testé ;
- déploiement progressif ;
- observabilité renforcée ;
- faible périmètre ;
- équipe expérimentée.

---

# 11. Autorisation et gouvernance

## Niveaux d’autorisation

| Niveau | Type de changement | Autorité |
|---|---|---|
| Niveau 1 | Standard | Préautorisation |
| Niveau 2 | Normal faible risque | Change Manager |
| Niveau 3 | Normal risque modéré | Responsable technique et métier |
| Niveau 4 | Majeur | CAB et Direction |
| Niveau 5 | Urgence | Emergency CAB |

---

## Séparation des responsabilités

Dans la mesure du possible :

- le demandeur ne doit pas être l’unique approbateur ;
- l’approbateur ne doit pas être l’unique exécutant ;
- l’exécutant ne doit pas être l’unique validateur ;
- la clôture doit être contrôlée.

---

## Traçabilité

Chaque décision d’approbation doit inclure :

- le décideur ;
- la date ;
- la décision ;
- les conditions ;
- les réserves ;
- les preuves.

---

# 12. Change Advisory Board

Le **Change Advisory Board — CAB** évalue les changements importants.

---

## Composition possible

- Change Manager ;
- responsable des opérations ;
- responsable sécurité ;
- architecte d’entreprise ;
- responsable applicatif ;
- responsable infrastructure ;
- responsable métier ;
- responsable des données ;
- représentant support ;
- fournisseur concerné.

---

## Missions

Le CAB :

- examine les changements ;
- évalue les impacts ;
- identifie les conflits ;
- confirme les fenêtres ;
- impose des conditions ;
- autorise ou reporte ;
- suit les changements majeurs.

---

## Emergency CAB

Le comité d’urgence est activé pour les changements critiques nécessitant une décision rapide.

Il comprend un nombre restreint de décideurs habilités.

---

# 13. Planification et calendrier

## 13.1 Calendrier des changements

Le calendrier doit faire apparaître :

- les changements planifiés ;
- les indisponibilités ;
- les périodes d’examen ;
- les campagnes nationales ;
- les clôtures administratives ;
- les sauvegardes majeures ;
- les changements fournisseurs.

---

## 13.2 Périodes sensibles

Aucun changement non essentiel ne doit être réalisé pendant :

- les inscriptions nationales ;
- les examens ;
- les affectations ;
- les campagnes d’abonnement ;
- les clôtures financières ;
- les périodes d’inspection ;
- les grandes opérations institutionnelles.

---

## 13.3 Fenêtre de maintenance

La fenêtre doit être définie selon :

- le niveau d’activité ;
- la criticité ;
- la durée ;
- le besoin de support ;
- la disponibilité des équipes ;
- le temps de retour arrière.

---

## 13.4 Gestion des conflits

Le système détecte :

- les changements simultanés ;
- les composants partagés ;
- les équipes surchargées ;
- les dépendances communes ;
- les risques de collision.

---

# 14. Mise en œuvre et validation

## 14.1 Prérequis

Avant le déploiement, les éléments suivants doivent être disponibles :

- procédure approuvée ;
- tests réussis ;
- sauvegarde vérifiée ;
- plan de rollback ;
- responsables mobilisés ;
- communication prête ;
- indicateurs de validation définis.

---

## 14.2 Stratégies de déploiement

### Déploiement classique

Arrêt, mise à jour, redémarrage.

---

### Rolling Deployment

Mise à jour progressive des instances.

---

### Blue-Green Deployment

Deux environnements sont maintenus :

```text
Blue — Version active

Green — Nouvelle version
```

Le trafic bascule après validation.

---

### Canary Release

La nouvelle version est exposée à un faible pourcentage d’utilisateurs avant généralisation.

---

### Feature Flags

Une fonctionnalité peut être activée ou désactivée sans redéploiement complet.

---

## 14.3 Critères de validation

- disponibilité conforme ;
- taux d’erreur acceptable ;
- performance conforme ;
- intégrité des données ;
- contrôles sécurité réussis ;
- fonctionnalités critiques opérationnelles ;
- absence d’incident majeur.

---

# 15. Retour arrière

Le plan de retour arrière doit préciser :

- les conditions de déclenchement ;
- la procédure ;
- le responsable ;
- le temps nécessaire ;
- les données à restaurer ;
- les dépendances ;
- les tests de validation.

---

## Déclencheurs possibles

- augmentation forte des erreurs ;
- indisponibilité ;
- corruption de données ;
- échec de migration ;
- vulnérabilité introduite ;
- régression fonctionnelle critique ;
- non-respect d’un SLA.

---

## Principes

- le rollback doit être testé ;
- les scripts doivent être versionnés ;
- les données doivent être sauvegardées ;
- la décision doit être rapide ;
- la communication doit être immédiate.

---

# 16. Changement d’urgence

Un changement d’urgence ne signifie pas un changement non contrôlé.

Il doit toujours comporter :

- un motif ;
- un responsable ;
- une autorisation ;
- un risque évalué ;
- un plan d’action ;
- un retour arrière ;
- une revue postérieure.

---

## Processus simplifié

```text
Incident critique

↓

Demande de changement d’urgence

↓

Analyse rapide

↓

Autorisation Emergency CAB

↓

Mise en œuvre

↓

↓

Revue obligatoire
```

---

## Exemples

- correction d’une vulnérabilité critique ;
- restauration d’un service national ;
- renouvellement immédiat d’un certificat expiré ;
- bascule vers un site de secours ;
- blocage d’un accès compromis.

## Infrastructure as Code

Les changements d’infrastructure doivent être :

- décrits dans du code ;
- versionnés ;
- relus ;
- testés ;
- reproductibles ;
- auditables.

---

## Policy as Code

Les règles d’autorisation et de conformité peuvent être automatisées.

Exemple :

```text

Approbation sécurité obligatoire
```

---

## Intelligence artificielle

L’IA peut :

- estimer le risque ;
- détecter les changements similaires ;
- prévoir les impacts ;
- recommander une fenêtre ;
- identifier des conflits ;
- suggérer un rollback ;
- analyser les résultats.

# 19. Cas d’usage EduWeb

- approbation institutionnelle ;

# 24. Conclusion

La **Gestion des Changements** permet à EduWeb de concilier innovation, rapidité de déploiement, stabilité opérationnelle et sécurité. Chaque évolution est analysée, autorisée, planifiée, testée, déployée et évaluée selon un niveau de contrôle proportionné à son risque.

Grâce à l’intégration du DevSecOps, de l’Infrastructure as Code, des déploiements progressifs, de l’observabilité et de l’intelligence artificielle, le cadre proposé réduit les incidents liés aux évolutions tout en accélérant la mise à disposition de nouveaux services. Il prépare directement la **Gestion des Configurations et de la CMDB**, décrite dans **OPS-007**, qui fournira une connaissance fiable des composants, des versions et des dépendances nécessaires à toute décision de changement.
