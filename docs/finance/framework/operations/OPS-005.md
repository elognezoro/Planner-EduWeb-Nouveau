# OPS-005 — Gestion des Problèmes (Enterprise Problem Management)

> **Objectif :** Définir le cadre de gestion des problèmes d’EduWeb afin d’identifier, d’analyser et d’éliminer les causes profondes des incidents récurrents ou majeurs, tout en réduisant durablement les risques, les interruptions de service et les coûts opérationnels.

# 1. Introduction

La gestion des incidents vise principalement à restaurer rapidement un service.

La gestion des problèmes poursuit un objectif différent :

> **Comprendre et éliminer les causes profondes des incidents.**

Un problème peut être identifié :

- à la suite d’un incident majeur ;
- après plusieurs incidents similaires ;
- grâce à une analyse prédictive ;
- lors d’un audit technique ;
- à partir d’une tendance anormale.

La gestion des problèmes permet de passer d’une exploitation réactive à une exploitation préventive.

---

# 2. Vision

EduWeb met en œuvre une gestion des problèmes :

- structurée ;
- proactive ;
- fondée sur les données ;
- orientée vers les causes profondes ;
- intégrée à la gestion des changements ;
- enrichie par l’intelligence artificielle.

L’objectif est de réduire durablement :

- la fréquence des incidents ;
- leur gravité ;
- leur durée ;
- leur coût ;
- leur impact sur les utilisateurs.

---

# 3. Objectifs

Le processus poursuit les objectifs suivants :

- identifier les causes profondes ;
- prévenir les incidents récurrents ;
- documenter les erreurs connues ;
- proposer des solutions permanentes ;
- réduire la dette technique ;
- améliorer la résilience ;
- capitaliser les connaissances ;
- soutenir l’amélioration continue.

---

# 4. Principes directeurs

La gestion des problèmes repose sur les principes suivants :

- Root Cause First
- Prevention Before Reaction
- Evidence-Based Analysis
- Blameless Investigation
- Knowledge by Default
- Cross-Functional Collaboration
- Risk-Based Prioritization
- Continuous Improvement
- Automation First
- Full Traceability

La recherche de la cause doit porter sur les systèmes, les processus et les conditions organisationnelles, et non sur la désignation de responsables individuels.

# 6. Définitions fondamentales

## 6.1 Problème

Cause réelle ou potentielle d’un ou de plusieurs incidents.

Exemple :

> Mauvaise configuration d’un pool de connexions provoquant des interruptions répétées.

---

## 6.2 Cause profonde

Facteur fondamental à l’origine du problème.

Exemple :

> Paramétrage par défaut inadapté à la charge réelle.

---

## 6.3 Erreur connue

Problème dont :

- la cause a été identifiée ;
- une solution définitive n’est pas encore déployée ;
- un contournement peut être disponible.

---

## 6.4 Contournement

Solution temporaire permettant de réduire ou supprimer l’impact d’un incident sans éliminer la cause profonde.

---

## 6.5 Action corrective

Action destinée à éliminer une cause déjà identifiée.

---

## 6.6 Action préventive

Action destinée à empêcher l’apparition d’un problème potentiel.

---

# 7. Typologie des problèmes

## 7.1 Problème réactif

Identifié après un ou plusieurs incidents.

Exemples :

- pannes répétées ;
- erreurs applicatives récurrentes ;
- indisponibilités fréquentes.

---

## 7.2 Problème proactif

Identifié avant tout incident majeur.

Exemples :

- capacité proche de la saturation ;
- certificat arrivant à expiration ;
- dérive progressive des performances ;
- dette technique critique.

---

## 7.3 Problème technique

Concerne :

- infrastructure ;
- réseau ;
- bases de données ;
- code ;
- configuration.

---

## 7.4 Problème organisationnel

Concerne :

- processus incomplets ;
- responsabilités mal définies ;
- communication insuffisante ;
- absence de contrôle.

---

## 7.5 Problème de sécurité

Concerne notamment :

- vulnérabilités ;
- mauvaises configurations ;
- contrôles insuffisants ;
- pratiques à risque.

---

## 7.6 Problème fournisseur

Résulte :

- d’une dépendance externe ;
- d’une limitation contractuelle ;
- d’un défaut de service tiers ;
- d’une rupture de support.

---

## 7.7 Problème métier

Affecte directement :

- les inscriptions ;
- les emplois du temps ;
- les réservations ;
- les validations administratives ;
- les parcours pédagogiques.

## 8.1 Détection

Un problème peut être détecté à partir :

- d’incidents récurrents ;
- d’un incident majeur ;
- d’une tendance observée ;
- d’une alerte prédictive ;
- d’un audit ;
- d’une recommandation AIOps.

---

## 8.2 Enregistrement

Le dossier de problème comprend :

- identifiant unique ;
- description ;
- incidents associés ;
- services concernés ;
- niveau de risque ;
- responsable ;
- données d’analyse ;
- historique.

---

## 8.3 Priorisation

La priorité dépend :

- de la fréquence des incidents ;
- de leur gravité ;
- de l’impact métier ;
- du risque futur ;
- du coût ;
- de la criticité du service.

---

## 8.4 Investigation

L’équipe collecte et analyse :

- métriques ;
- logs ;
- traces ;
- changements récents ;
- configurations ;
- historiques ;
- dépendances ;
- témoignages utilisateurs.

---

## 8.5 Résolution permanente

La résolution peut nécessiter :

- un correctif logiciel ;
- une modification d’architecture ;
- une évolution de processus ;
- un changement de configuration ;
- une montée de version ;
- un remplacement de fournisseur ;
- une formation.

# 10. Analyse des causes profondes

Plusieurs méthodes peuvent être utilisées.

---

## 10.1 Méthode des cinq pourquoi

Exemple :

```text
Pourquoi le service est-il devenu indisponible ?

Parce que la base de données était saturée.

Pourquoi était-elle saturée ?

Parce que trop de connexions restaient ouvertes.

Pourquoi restaient-elles ouvertes ?

Parce qu’un microservice ne libérait pas correctement les connexions.

Pourquoi ?

Parce qu’une erreur n’était pas gérée dans le code.

Pourquoi cette erreur n’a-t-elle pas été détectée ?

Parce que les tests de charge et de résilience étaient insuffisants.
```

Cause profonde :

> Couverture insuffisante des tests de charge et mauvaise gestion des connexions.

---

## 10.2 Diagramme d’Ishikawa

Les causes sont recherchées dans plusieurs catégories :

- méthodes ;
- matériels ;
- logiciels ;
- données ;
- personnes ;
- environnement ;
- gouvernance.

---

## 10.3 Analyse de Pareto

Le principe consiste à identifier les causes responsables de la majorité des incidents.

Exemple :

> 20 % des causes produisent 80 % des interruptions.

---

## 10.4 Arbre des défaillances

Le système représente les événements conduisant à une panne.

```text
Indisponibilité du service

├── Base de données indisponible
├── Réseau interrompu
├── Authentification en échec
└── Saturation applicative
```

---

## 10.5 Analyse chronologique

Reconstitution complète des événements :

```text
10:00 — Déploiement

10:12 — Hausse du taux d’erreur

10:18 — Saturation mémoire

10:22 — Redémarrage automatique

10:25 — Service indisponible
```

---

## 10.6 Analyse causale assistée par IA

L’IA peut :

- corréler les événements ;
- comparer les incidents ;
- identifier les variables communes ;
- suggérer des causes probables ;
- estimer le niveau de confiance.

La validation humaine reste obligatoire.

# 11. Gestion des erreurs connues

Lorsqu’une cause est identifiée mais non encore supprimée, une erreur connue est créée.

---

## Contenu d’une erreur connue

- identifiant ;
- symptômes ;
- cause ;
- services impactés ;
- contournement ;
- risques ;
- correctif prévu ;
- date cible ;
- responsable.

---

## Exemple

```text
Erreur connue : KE-BOOKING-004

Symptôme :
Certaines réservations échouent à forte charge.

Cause :
Verrouillage concurrent sur la table des disponibilités.

Contournement :
Relancer automatiquement la transaction après 3 secondes.

Solution permanente :
Refonte du mécanisme de verrouillage.
```

---

## Utilité

La base d’erreurs connues permet :

- d’accélérer la résolution des incidents ;
- de limiter les diagnostics répétitifs ;
- d’harmoniser les réponses ;
- d’améliorer le support utilisateur.

---

# 12. Mesures correctives et préventives

## 12.1 Actions correctives

Exemples :

- corriger un défaut logiciel ;
- modifier une configuration ;
- renforcer la capacité ;
- remplacer un composant ;
- revoir une procédure.

---

## 12.2 Actions préventives

Exemples :

- automatiser des contrôles ;
- renforcer les tests ;
- ajouter une alerte ;
- améliorer la documentation ;
- former les équipes ;
- supprimer une dépendance critique.

---

## 12.3 Validation

Une action est validée lorsque :

- le problème ne se reproduit plus ;
- les indicateurs sont stabilisés ;
- les risques sont réduits ;
- aucun effet secondaire majeur n’est observé.

---

## 12.4 Revue d’efficacité

Une période d’observation peut être définie.

| Criticité | Période minimale recommandée |
|---|---:|
| Critique | 30 jours |
| Élevée | 21 jours |
| Moyenne | 14 jours |
| Faible | 7 jours |

# 15. Automatisation et AIOps

L’AIOps peut améliorer la gestion des problèmes.

---

## Détection de récurrence

L’IA regroupe automatiquement les incidents présentant :

- les mêmes symptômes ;
- les mêmes composants ;
- des chronologies similaires ;
- des causes probables communes.

---

## Analyse de dépendances

Le graphe de services permet d’identifier :

- les composants centraux ;
- les points uniques de défaillance ;
- les chaînes de propagation.

---

## Suggestion de cause

Le moteur compare le problème à :

- l’historique ;
- la base d’erreurs connues ;
- les changements récents ;
- les données d’observabilité.

---

## Priorisation prédictive

L’IA évalue :

- la probabilité de récurrence ;
- l’impact futur ;
- le coût potentiel ;
- la criticité métier.

---

## Génération de plans d’action

Le système peut suggérer :

- un correctif ;
- un test ;
- une modification de configuration ;
- une action préventive ;
- un changement d’architecture.

---

## Limites

L’automatisation ne doit pas :

- clôturer seule un problème critique ;
- imposer un changement irréversible ;
- masquer une incertitude ;
- remplacer l’analyse humaine ;
- supprimer les preuves.

---

# 16. Cas d’usage EduWeb

## Exemple 1 — EduWeb Planner

Plusieurs établissements signalent des échecs intermittents lors de la génération des emplois du temps.

L’analyse montre :

- une consommation mémoire croissante ;
- des arrêts fréquents du moteur ;
- une absence de libération de certaines structures de calcul.

Cause profonde :

> Fuite mémoire dans le moteur d’optimisation.

Actions :

- correctif logiciel ;
- tests de charge ;
- alerte mémoire ;
- revue du code.

---

## Exemple 2 — EduWeb Governance

Des décisions administratives restent régulièrement bloquées.

L’investigation révèle :

- une étape de validation non attribuée ;
- une règle métier ambiguë ;
- une absence d’escalade automatique.

Cause profonde :

> Défaut de conception du workflow.

Solution :

- clarification des responsabilités ;
- règle d’escalade ;
- correction du workflow ;
- tableau de bord de suivi.

---

## Exemple 3 — EduWeb Booking

Des doubles réservations apparaissent de manière intermittente.

Cause profonde :

> Mécanisme de concurrence insuffisant entre deux transactions simultanées.

Solution :

- verrouillage optimiste ;
- contrôle d’idempotence ;
- test de concurrence ;
- journalisation renforcée.

---

## Exemple 4 — E-School EduWeb

Les apprenants connaissent des déconnexions fréquentes à certaines heures.

L’analyse identifie :

- une durée de session trop courte ;
- une synchronisation incorrecte entre serveurs ;
- un équilibrage de charge incomplet.

Solution :

- stockage partagé des sessions ;
- synchronisation ;
- modification des paramètres ;
- tests de montée en charge.

---

## Exemple 5 — Ministère

À chaque campagne nationale, les performances se dégradent.

Le problème n’est pas seulement lié à la capacité.

L’analyse révèle :

- des requêtes non optimisées ;
- une architecture centralisée ;
- une absence de cache ;
- des traitements synchrones.

Solution permanente :

- optimisation des requêtes ;
- cache distribué ;
- traitements asynchrones ;
- architecture élastique ;
- planification de capacité.

# 21. Conclusion

La **Gestion des Problèmes** constitue le mécanisme d’apprentissage structurel de l’exploitation EduWeb. Alors que la gestion des incidents restaure les services, la gestion des problèmes recherche et élimine les causes profondes afin d’empêcher la réapparition des interruptions, des dégradations et des erreurs.

En combinant l’analyse des incidents, l’observabilité, la base des erreurs connues, les méthodes d’analyse causale, les actions correctives et préventives ainsi que les capacités AIOps, ce cadre permet de réduire durablement les risques opérationnels et la dette technique. Il alimente directement la **Gestion des Changements**, décrite dans **OPS-006**, afin que les solutions permanentes soient mises en œuvre de manière contrôlée, traçable et sécurisée.
