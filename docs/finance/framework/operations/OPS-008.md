# 1. Introduction

La mise à disposition d’une nouvelle fonctionnalité ne se limite pas à transférer du code vers un serveur de production.

Elle implique la maîtrise :

- du contenu de la version ;
- des dépendances ;
- des environnements ;
- des artefacts ;
- des configurations ;
- des tests ;
- des données ;
- de la sécurité ;
- du retour arrière ;
- de la communication aux utilisateurs.

La gestion des versions et des déploiements transforme les changements autorisés en composants effectivement utilisables dans les environnements EduWeb.

Elle doit garantir que chaque mise en production est :

- planifiée ;
- contrôlée ;
- reproductible ;
- sécurisée ;
- observable ;
- réversible ;
- documentée.

---

# 2. Vision

EduWeb adopte une gestion des versions et des déploiements :

- industrialisée ;
- automatisée ;
- progressive ;
- intégrée au DevSecOps ;
- fondée sur des artefacts immuables ;
- pilotée par des politiques ;
- traçable de bout en bout ;
- compatible avec les environnements Cloud, hybrides et distribués.

L’objectif est de livrer plus rapidement de nouvelles capacités tout en réduisant les risques d’interruption, de régression et de vulnérabilité.

---

# 3. Objectifs

Le processus poursuit les objectifs suivants :

- garantir l’intégrité des versions ;
- standardiser les mises en production ;
- réduire les erreurs humaines ;
- automatiser les déploiements ;
- assurer la séparation des environnements ;

- renforcer la sécurité de la chaîne logicielle ;

# 6. Concepts fondamentaux

## 6.1 Version

Ensemble cohérent et identifié de composants destinés à être testés, publiés ou déployés.

Une version peut contenir :

- du code applicatif ;
- des scripts ;
- des configurations ;
- des migrations de données ;
- des modèles IA ;
- des règles métier ;
- de la documentation ;
- des manifestes d’infrastructure.

---

## 6.2 Release

Version officiellement approuvée pour une mise à disposition dans un ou plusieurs environnements.

---

## 6.3 Déploiement

Action technique consistant à installer, configurer ou activer une version dans un environnement cible.

---

## 6.4 Publication

Action rendant une version disponible dans un référentiel officiel.

---

## 6.5 Artefact

Composant produit par le processus de construction.

Exemples :

- image de conteneur ;
- paquet logiciel ;
- bibliothèque ;
- fichier statique ;
- modèle d’intelligence artificielle ;
- manifeste Kubernetes ;
- script de migration ;
- archive applicative.

---

## 6.6 Promotion

Passage d’un même artefact validé d’un environnement à un autre.

```text
Développement

↓

Test

↓

Préproduction

↓

Production
```

---

## 6.7 Rollback

Retour vers une version antérieure stable.

---

## 6.8 Rollforward

Correction d’un défaut par le déploiement d’une version plus récente.

---

## 6.9 Feature Flag

Mécanisme permettant d’activer ou de désactiver une fonctionnalité sans redéployer l’ensemble de l’application.

---

# 7. Typologie des versions

## 7.1 Version majeure

Introduit des évolutions significatives ou potentiellement incompatibles.

Exemple :

```text
EduWeb Planner 3.0.0
```

Peut comprendre :

- une nouvelle architecture ;
- une refonte fonctionnelle ;
- une modification importante du modèle de données ;
- une rupture de compatibilité.

---

## 7.2 Version mineure

Ajoute des fonctionnalités compatibles avec la version existante.

Exemple :

```text
EduWeb Planner 3.2.0
```

---

## 7.3 Version corrective

Corrige des anomalies sans introduire de changements fonctionnels majeurs.

Exemple :

```text
EduWeb Planner 3.2.4
```

---

## 7.4 Correctif d’urgence

Version publiée rapidement pour corriger :

- un incident critique ;
- une vulnérabilité majeure ;
- une perte de service ;
- un défaut bloquant.

---

## 7.5 Version pilote

Déployée auprès d’un groupe limité afin de valider :

- la stabilité ;
- l’usage ;
- la performance ;
- l’acceptabilité.

---

## 7.6 Version expérimentale

Utilisée dans un environnement isolé pour tester une innovation.

---

## 7.7 Version réglementaire

Mise en production pour satisfaire une obligation légale, institutionnelle ou contractuelle.

---

## 7.8 Version de modèle IA

Contient un modèle d’intelligence artificielle avec :

- son identifiant ;
- ses données d’entraînement ;
- ses hyperparamètres ;
- ses performances ;
- ses limites ;
- son niveau d’approbation.

---

## 8.1 Planification

La version est associée à :

- un objectif ;
- une portée ;
- une échéance ;
- une liste de fonctionnalités ;
- des risques ;
- des dépendances ;
- un responsable ;
- un changement autorisé.

---

## 8.2 Construction

Le système construit automatiquement les artefacts à partir :

- du code source ;
- des dépendances déclarées ;
- des manifestes ;
- des configurations versionnées.

---

## 8.3 Test

La version est soumise à :

- des tests unitaires ;
- des tests d’intégration ;
- des tests fonctionnels ;
- des tests de sécurité ;
- des tests de performance ;
- des tests de résilience ;
- des tests de compatibilité ;
- des tests métier.

---

## 8.4 Publication

Les artefacts validés sont publiés dans un référentiel officiel.

Ils reçoivent :

- un identifiant ;
- une version ;
- une signature ;
- une empreinte ;
- une date ;
- un propriétaire ;
- une durée de conservation.

---

## 8.5 Déploiement

La version est déployée selon une stratégie approuvée.

---

## 8.6 Validation

La validation vérifie :

- la disponibilité ;
- les performances ;
- la sécurité ;
- l’intégrité des données ;
- les indicateurs métier ;
- les retours utilisateurs.

---

## 8.7 Retrait

Une version devient obsolète lorsqu’elle :

- n’est plus supportée ;
- présente un risque ;
- est remplacée ;
- devient incompatible ;
- ne respecte plus les standards.

# 10. Gestion du versionnement

## 10.1 Versionnement sémantique

Le format recommandé est :

```text
MAJEUR.MINEUR.CORRECTIF
```

Exemple :

```text
4.3.2
```

Interprétation :

- 4 : version majeure ;
- 3 : évolution fonctionnelle compatible ;
- 2 : correctif.

---

## 10.2 Versionnement des API

Les API doivent exposer explicitement leur version.

Exemples :

```text
/api/v1/etablissements

/api/v2/etablissements
```

Une politique de dépréciation doit préciser :

- la date d’annonce ;
- la période de coexistence ;
- la date de retrait ;
- les modalités de migration.

---

## 10.3 Versionnement des données

Les schémas de données doivent être versionnés.

Chaque évolution comprend :

- un script de migration ;
- un script de validation ;
- un mécanisme de restauration ;
- une documentation de compatibilité.

---

## 10.4 Versionnement des configurations

Les configurations doivent être :

- conservées dans un référentiel ;
- versionnées ;
- revues ;
- approuvées ;
- automatiquement déployées.

---

## 10.5 Versionnement des modèles IA

Chaque modèle possède :

- un identifiant unique ;
- une version ;
- un jeu de données de référence ;
- des métriques ;
- une fiche de modèle ;
- une date d’approbation ;
- un statut de production.

---

## 10.6 Convention de nommage

Exemple :

```text
eduweb-planner-engine:3.4.1

eduweb-governance-api:2.7.0

eduweb-booking-web:1.9.3
```

# 11. Gestion des artefacts

## 11.1 Exigences

Chaque artefact doit être :

- unique ;
- immuable ;
- identifiable ;
- signé ;
- vérifiable ;
- traçable ;
- reproductible.

---

## 11.2 Métadonnées minimales

| Attribut | Description |
|---|---|
| Identifiant | Référence unique |
| Nom | Désignation |
| Version | Numéro officiel |
| Empreinte | Somme de contrôle |
| Signature | Preuve d’authenticité |
| Date | Date de construction |
| Source | Révision du code |
| Pipeline | Processus de construction |
| Propriétaire | Équipe responsable |
| Statut | Test, validé, retiré |

---

## 11.3 Immuabilité

Un artefact publié ne doit jamais être remplacé sous le même numéro de version.

Toute modification impose une nouvelle version.

---

## 11.4 Signature

La signature permet de vérifier :

- l’origine ;
- l’intégrité ;
- l’absence de modification.

---

## 11.5 Nomenclature des référentiels

Les artefacts peuvent être regroupés par :

- plateforme ;
- composant ;
- environnement ;
- niveau de sensibilité ;
- statut.

---

## 11.6 Politique de rétention

| Type d’artefact | Rétention indicative |
|---|---:|
| Version active | Durée de vie complète |
| Version précédente stable | 24 mois |
| Correctif de sécurité | 36 mois |
| Version expérimentale | 6 mois |
| Artefact non validé | 90 jours |
| Version réglementaire | Selon exigence légale |

## 12.7 Secours

Environnement destiné à assurer la continuité ou la reprise d’activité.

- des identités ;
- des réseaux ;
- des données ;
- des secrets ;

- des accès administratifs.

# 13. Stratégies de déploiement

## 13.1 Déploiement Big Bang

La totalité de la nouvelle version remplace l’ancienne simultanément.

Avantages :

- simplicité ;
- durée courte.

Risques :

- impact étendu ;
- rollback complexe ;
- faible progressivité.

Il doit être réservé aux environnements simples ou aux changements maîtrisés.

---

## 13.2 Rolling Deployment

Les instances sont mises à jour progressivement.

```text
Instance 1

↓

Instance 2

↓

Instance 3

↓

Instance 4
```

Avantages :

- continuité de service ;
- réduction du risque.

---

## 13.3 Blue-Green Deployment

Deux environnements identiques coexistent.

```text
Blue
Version actuelle

Green
Nouvelle version
```

Après validation, le trafic bascule vers Green.

Avantages :

- rollback rapide ;
- interruption minimale.

---

## 13.4 Canary Release

La nouvelle version est déployée pour une faible proportion d’utilisateurs.

Exemple :

```text
5 % des utilisateurs

↓

20 %

↓

50 %

↓

100 %
```

La progression dépend des résultats observés.

---

## 13.5 Déploiement par établissement

Une version peut être activée progressivement :

- dans un établissement pilote ;
- dans une région ;
- dans plusieurs académies ;
- au niveau national.

---

## 13.6 Déploiement par fonctionnalités

Les Feature Flags permettent une activation ciblée selon :

- le rôle ;
- l’établissement ;
- la région ;
- le type d’abonnement ;
- l’environnement ;
- la population pilote.

---

## 13.7 Shadow Deployment

La nouvelle version reçoit une copie du trafic sans produire la réponse finale.

Elle permet de comparer :

- les performances ;
- les résultats ;
- les erreurs ;
- les décisions.

Cette stratégie est particulièrement utile pour les moteurs IA et algorithmiques.

---

## 13.8 Déploiement immuable

Les composants existants ne sont pas modifiés.

De nouvelles instances sont créées, puis les anciennes sont retirées.

## 14.1 Gates de qualité

Une version ne peut être promue que si elle respecte les seuils définis.

Exemples :

- tests unitaires réussis ;
- absence de vulnérabilité critique ;
- qualité du code conforme ;
- performance acceptable ;
- migration validée ;
- documentation disponible ;
- changement approuvé.

---

## 14.2 Gates de sécurité

Le pipeline doit bloquer une version en cas de :

- secret exposé ;
- composant vulnérable critique ;
- signature invalide ;
- image non approuvée ;
- licence interdite ;
- configuration non conforme.

---

## 14.3 Approbation manuelle

Une validation humaine peut rester obligatoire avant :

- la production ;
- un changement majeur ;
- une migration de données ;
- un déploiement national ;
- un modèle IA sensible.

# 15. Validation et critères de promotion

## 15.1 Critères techniques

- application disponible ;
- taux d’erreur conforme ;
- temps de réponse acceptable ;
- ressources maîtrisées ;
- intégrations fonctionnelles ;
- journaux sans anomalie critique.

---

## 15.2 Critères fonctionnels

- parcours critiques réussis ;
- résultats conformes ;
- règles métier validées ;
- absence de régression bloquante.

---

## 15.3 Critères de sécurité

- contrôles d’accès opérationnels ;
- vulnérabilités critiques absentes ;
- secrets protégés ;
- journalisation active ;
- politiques conformes.

---

## 15.4 Critères de données

- migration complète ;
- intégrité vérifiée ;
- volumes conformes ;
- sauvegarde disponible ;
- absence de perte ou duplication.

---

## 15.5 Critères métier

- indicateurs métier stables ;
- aucune interruption critique ;
- utilisateurs pilotes satisfaits ;
- résultats attendus obtenus.

---

## 15.6 Décision de promotion

```text
Tous les critères respectés

↓

Promotion

Sinon

↓

Correction ou rollback
```

# 16. Gestion des migrations de données

Les migrations de données constituent l’un des principaux risques de déploiement.

---

## 16.1 Exigences

Toute migration doit comporter :

- un inventaire des données ;
- une cartographie des transformations ;
- un script versionné ;
- une sauvegarde ;
- un test sur copie réaliste ;
- une estimation de durée ;
- une validation ;
- un plan de retour.

---

## 16.2 Stratégies

### Migration directe

Transformation immédiate du schéma.

---

### Expand and Contract

La structure est étendue avant le retrait progressif de l’ancien format.

```text
Ajouter le nouveau champ

↓

Maintenir les deux formats

↓

Migrer les données

↓

Basculer les applications

↓

Supprimer l’ancien champ
```

---

### Double écriture

Les données sont temporairement enregistrées dans l’ancien et le nouveau format.

---

### Migration asynchrone

La migration est exécutée progressivement en arrière-plan.

---

## 16.3 Validation

Les contrôles portent sur :

- le nombre d’enregistrements ;
- les totaux ;
- les relations ;
- les doublons ;
- les données orphelines ;
- les règles d’intégrité ;
- les performances.

---

# 17. Retour arrière et récupération

## 17.1 Conditions de rollback

Le rollback est déclenché en cas de :

- panne critique ;
- taux d’erreur supérieur au seuil ;
- dégradation importante ;
- perte de données ;
- vulnérabilité ;
- régression métier ;
- incompatibilité.

---

## 17.2 Mécanismes

- restauration de la version précédente ;
- bascule Blue-Green ;
- désactivation d’une Feature Flag ;
- restauration de sauvegarde ;
- rollback de migration ;
- bascule vers le site de secours.

---

## 17.3 Rollback automatisé

Exemple :

```text
Taux d’erreur > 5 %

pendant 5 minutes

↓

Arrêt de la progression

↓

Retour à la version précédente

↓

Création d’un incident
```

---

## 17.4 Limites

Un rollback peut être difficile lorsque :

- les données ont changé ;
- des transactions externes ont été exécutées ;
- une version n’est plus compatible ;
- des utilisateurs ont produit de nouveaux contenus.

Dans ces cas, le rollforward peut être préférable.

---

# 18. Sécurité des versions et déploiements

## 18.1 Sécurité de la chaîne logicielle

La chaîne doit protéger :

- le code ;
- les dépendances ;
- les pipelines ;
- les identités ;
- les artefacts ;
- les environnements ;
- les secrets.

---

## 18.2 Contrôles

- authentification forte ;
- moindre privilège ;
- signatures ;
- chiffrement ;
- journalisation ;
- séparation des tâches ;
- approbation des artefacts ;
- contrôle des dépendances ;
- analyse des images ;
- protection contre les modifications.

---

## 18.3 Software Bill of Materials

Chaque version doit idéalement disposer d’une liste de ses composants logiciels.

Cette liste permet :

- l’identification des dépendances ;
- la recherche de vulnérabilités ;
- la gestion des licences ;
- l’analyse d’impact.

---

## 18.4 Gestion des secrets

Les secrets ne doivent jamais être inclus dans :

- le code source ;
- les images ;
- les scripts ;
- les journaux ;
- les fichiers publics.

Ils doivent provenir d’un coffre-fort sécurisé.

---

## 18.5 Comptes de service

Les pipelines utilisent des identités dédiées avec :

- des droits minimaux ;
- une durée limitée ;
- une journalisation complète ;
- une rotation régulière.

# 20. Automatisation et GitOps

## 20.1 GitOps

Dans une approche GitOps, l’état souhaité des environnements est décrit dans un référentiel Git.

```text
État déclaré dans Git

↓

Contrôleur GitOps

↓

Comparaison avec l’état réel

↓

Application des changements

↓

Vérification continue
```

---

## 20.2 Avantages

- traçabilité ;
- reproductibilité ;
- rollback ;
- revue ;
- automatisation ;
- réduction des dérives.

---

## 20.3 Détection des dérives

Le système compare :

- la configuration souhaitée ;
- la configuration réellement déployée.

Toute différence génère :

- une alerte ;
- une correction automatique ;
- ou une demande de validation.

## 20.4 Mise à jour de la CMDB

Après chaque déploiement réussi, la CMDB reçoit automatiquement :

- la version ;
- la date ;
- l’environnement ;
- les composants ;
- les relations ;
- le statut.

L’IA peut :

- recommander une stratégie de déploiement ;
- estimer le risque ;
- détecter des anomalies ;
- prévoir les impacts ;
- comparer les performances ;
- proposer un rollback ;
- rédiger des notes de version ;
- identifier des dépendances oubliées.

# 27. Conclusion

La **Gestion des Versions et des Déploiements** permet à EduWeb de transformer les développements, les changements autorisés et les évolutions d’architecture en services réellement disponibles pour les utilisateurs, tout en maintenant un niveau élevé de qualité, de sécurité et de continuité.

L’utilisation d’artefacts immuables, de pipelines automatisés, de stratégies de déploiement progressif, de mécanismes de validation continue, de signatures et de politiques de retour arrière réduit fortement les risques associés aux mises en production. L’intégration avec la gestion des changements, la CMDB, l’observabilité, le DevSecOps et le SRE garantit une traçabilité complète de chaque version, depuis le code source jusqu’au service exploité.

Cette architecture prépare directement la **Continuité d’Activité**, décrite dans **OPS-009**, en s’assurant que les plateformes peuvent évoluer, être restaurées et continuer à fonctionner même en cas de défaillance, d’incident majeur ou de perturbation institutionnelle.
