# 1. Introduction

La performance représente la capacité d’un système à fournir un résultat attendu dans un délai, avec un niveau de qualité et une consommation de ressources acceptables.

Une plateforme peut être disponible tout en étant pratiquement inutilisable en raison :

- d’un temps de réponse excessif ;
- d’une lenteur des traitements ;
- d’une saturation des bases ;
- d’une latence réseau élevée ;
- d’un défaut de concurrence ;
- d’un algorithme trop coûteux ;
- d’une interface trop lourde ;
- d’une mauvaise optimisation mobile ;
- d’une dépendance externe défaillante.

La gestion des performances vise à garantir que les services EduWeb restent :

- rapides ;
- réactifs ;
- stables ;
- prévisibles ;
- mesurables ;
- adaptés aux conditions réelles d’utilisation.

Elle complète la gestion de la capacité :

```text
Capacité
=
Ressources disponibles

Performance
=
Qualité obtenue avec ces ressources
```

Une augmentation de capacité ne garantit pas automatiquement une meilleure performance. Une analyse technique, applicative et métier reste nécessaire.

# 2. Vision

EduWeb met en œuvre une gestion des performances :

- centrée sur l’expérience utilisateur ;
- fondée sur l’observabilité ;
- proactive ;
- intégrée au cycle de développement ;
- mesurée de bout en bout ;
- sensible aux contextes de faible connectivité ;
- automatisée lorsque cela est pertinent ;
- alignée sur les objectifs métier.

La performance doit être considérée comme une exigence fonctionnelle et architecturale, et non comme une correction tardive réalisée après la mise en production.

# 6. Concepts fondamentaux

## 6.1 Temps de réponse

Durée entre l’émission d’une demande et la réception du résultat.

```text
Temps de réponse =
Temps réseau
+
Temps de traitement
+
Temps d’attente
+
Temps d’affichage
```

---

## 6.2 Latence

Délai nécessaire pour qu’une information traverse un système ou un réseau.

---

## 6.3 Débit

Volume d’opérations traitées pendant une unité de temps.

Exemples :

- requêtes par seconde ;
- dossiers par minute ;
- emplois du temps par heure ;
- fichiers par seconde ;
- notifications par minute.

---

## 6.4 Concurrence

Nombre d’utilisateurs, de sessions ou de traitements exécutés simultanément.

---

## 6.5 Taux d’erreur

Proportion des opérations ayant échoué.

```text
Taux d’erreur =
Nombre d’opérations en erreur
/
Nombre total d’opérations
× 100
```

---

## 6.6 Apdex

Indicateur synthétique de satisfaction utilisateur fondé sur le temps de réponse.

Les opérations sont classées en :

- satisfaisantes ;
- tolérables ;
- frustrantes.

---

## 6.7 Percentile

Valeur sous laquelle se situe une proportion donnée des mesures.

Exemple :

```text
P95 = 2 secondes
```

Cela signifie que 95 % des requêtes sont traitées en deux secondes ou moins.

---

## 6.8 Goulot d’étranglement

Composant limitant la performance globale.

---

## 6.9 Régression de performance

Dégradation introduite par :

- une nouvelle version ;
- un changement de configuration ;
- une évolution de données ;
- une dépendance ;
- une modification d’infrastructure.

---

## 6.10 Budget de performance

Limite maximale acceptable pour une métrique donnée.

Exemples :

- taille maximale d’une page ;
- temps maximal de chargement ;
- nombre maximal de requêtes ;
- latence maximale d’une API ;
- temps maximal de calcul.

# 17. Budgets de performance

## 17.1 Principe

Un budget fixe une limite à ne pas dépasser.

---

## 17.2 Exemple web

| Élément | Budget indicatif |
|---|---:|
| Page initiale compressée | ≤ 1 Mo |
| JavaScript initial | ≤ 300 Ko |
| Temps de chargement P75 | ≤ 2,5 s |
| Réponse API P95 | ≤ 500 ms |
| Nombre de requêtes initiales | ≤ 50 |

Les valeurs doivent être adaptées au contexte réel.

---

## 17.3 Exemple mobile

| Élément | Budget indicatif |
|---|---:|
| Démarrage à froid | ≤ 3 s |
| Synchronisation légère | ≤ 5 s |
| Consommation par parcours | Limitée |
| Taille de cache | Contrôlée |
| Taux d’échec de synchronisation | < 1 % |

---

## 17.4 Exemple algorithmique

| Traitement | Budget indicatif |
|---|---:|
| Génération simple | ≤ 30 s |
| Génération complexe | ≤ 5 min |
| Proposition intermédiaire | ≤ 10 s |
| Validation des contraintes | ≤ 2 s |

---

## 17.5 Enforcement

Les budgets doivent pouvoir bloquer :

- une fusion ;
- un build ;
- un déploiement ;
- une promotion.

# 19. Tests de performance

## 19.1 Test de charge

Évalue le comportement sous une charge attendue.

---

## 19.2 Test de stress

Augmente la charge jusqu’à la rupture.

Il permet d’identifier :

- le point de saturation ;
- le comportement d’échec ;
- la capacité de récupération.

---

## 19.3 Test de pic

Simule une montée rapide.

---

## 19.4 Test d’endurance

Maintient une charge prolongée.

Il détecte notamment :

- les fuites mémoire ;
- l’accumulation de connexions ;
- la dégradation progressive ;
- les problèmes de stockage.

---

## 19.5 Test de volume

Évalue le comportement avec de grands volumes de données.

---

## 19.6 Test de concurrence

Simule plusieurs opérations simultanées sur les mêmes ressources.

---

## 19.7 Test de résilience

Combine performance et défaillances.

Exemples :

- arrêt d’une instance ;
- latence de base ;
- indisponibilité d’API ;
- perte réseau.

---

## 19.8 Données de test

Les données doivent être :

- réalistes ;
- anonymisées ;
- représentatives ;
- suffisamment volumineuses ;
- diversifiées.

---

## 19.9 Environnement

L’environnement de test doit être aussi proche que possible de la production.

---

# 38. Conclusion

La **Gestion des Performances** permet à EduWeb de garantir que ses services ne soient pas seulement disponibles, mais également rapides, réactifs, stables et adaptés aux conditions réelles d’utilisation.

Elle associe la mesure de l’expérience utilisateur, l’APM, les métriques, les journaux, les traces distribuées, le profiling, les tests de charge, les budgets de performance et l’analyse métier. Cette vision de bout en bout permet de détecter les régressions, d’identifier précisément les goulots d’étranglement et de valider objectivement les optimisations.

L’attention portée aux terminaux mobiles, aux connexions limitées, aux traitements algorithmiques et aux opérations nationales garantit une performance cohérente avec les réalités des établissements et des utilisateurs EduWeb.

La performance contribue directement à la disponibilité réelle d’un service. Le document suivant, **OPS-013 — Gestion de la Disponibilité**, définira les mécanismes permettant de mesurer, concevoir et améliorer la capacité des plateformes EduWeb à rester accessibles et fonctionnelles conformément aux engagements de service.
